# Product Spec — #487 spec-me 다이어그램 산출물·렌더·PR 미리보기

## 1. 문제와 맥락

현재 `spec-me` 산출물은 요구사항과 설계 판단을 텍스트 중심으로 전달한다. 사용자 흐름, 상태 전이, 클래스 책임을 같은 수준에서 빠르게 검토하기 어렵고, PR에서 다이어그램을 바로 확인할 일관된 구조도 없다.

## 2. 목표와 기대 결과

- 새로 생성되는 Spec이 단계에 맞는 PlantUML 원본과 렌더 이미지를 제공한다.
- 요구사항, 흐름, 구조, 상태의 관계를 검토자가 Markdown과 PR에서 빠르게 확인한다.
- 다이어그램 원본·렌더 결과·요구사항 식별자 사이 추적성을 유지한다.
- PR 본문은 짧은 요약을 먼저 보여 주고, 상세 그림은 접어서 제공한다.

## 3. 사용자와 액터

| 액터 | 목적 |
|---|---|
| Spec 작성자 | 요구사항과 설계 결정을 다이어그램으로 검토·기록한다. |
| 구현자 | 승인된 Spec의 흐름·구조·상태를 구현 계획과 코드에 반영한다. |
| PR 검토자 | 변경 의도와 다이어그램을 PR에서 빠르게 검토한다. |
| `spec-me` | 단계별 Spec과 필요한 다이어그램 산출물을 생성·검증한다. |
| `gh-open-pr` | PR 본문에 요약과 변경 다이어그램 미리보기를 구성한다. |

## 4. 용어

| 용어 | 정의 |
|---|---|
| Product 다이어그램 | 사용자·업무 관점의 유스케이스, 액티비티, 필요 시 업무 상태 다이어그램. |
| Architecture 다이어그램 | 설계 책임 관점의 클래스, 필요 시 설계 상태 다이어그램. |
| 흐름 변경 | 사용자 또는 시스템이 시작·처리·분기·종료하는 업무 흐름의 신설 또는 변경. |
| 원본 | 사람이 편집하는 `.puml` 파일. |
| 렌더 산출물 | 원본에서 생성한 SVG 또는 PNG 이미지. |

## 5. 핵심 유스케이스

### UC-001 — Product Spec 흐름 기록

1. `spec-me`가 Product Spec을 확정한다.
2. 핵심 사용자 흐름이 새로 생기거나 변경되었으면 유스케이스·액티비티 다이어그램을 작성한다.
3. 독립 검토가 필요한 업무 상태가 있으면 업무 상태 다이어그램을 작성한다.
4. 원본을 렌더하고 `product-spec.md`에서 SVG를 참조한다.

### UC-002 — Architecture Spec 구조·상태 기록

1. `spec-me`가 Architecture Spec을 확정한다.
2. 구조 모델이 적용되면 클래스 다이어그램을 작성한다.
3. 설계 책임을 설명할 상태 전이가 있으면 설계 상태 다이어그램을 작성한다.
4. 원본을 렌더하고 `architecture-spec.md`에서 SVG를 참조한다.

### UC-003 — PR에서 변경 다이어그램 검토

1. `gh-open-pr`가 변경 내용을 요약한다.
2. `eli5` 설명 방식으로 PR 첫 부분에 한 문장과 최대 세 단계의 흐름을 제시한다.
3. 변경된 다이어그램을 각각 독립적인 접기 블록으로 PR 본문에 넣는다.
4. 검토자가 필요한 그림만 펼쳐 SVG 미리보기를 확인한다.

## 6. 규칙과 불변 조건

- 요구사항 명세의 단일 원본은 `product-spec.md`다. 별도 `requirements.md`를 만들지 않는다.
- 다이어그램은 모든 Spec에 형식적으로 만들지 않는다. 해당 관점이 필요한 경우에만 만든다.
- 흐름이 신설·변경되면 해당 유스케이스·액티비티 다이어그램을 반드시 생성 또는 갱신한다.
- 업무 상태와 설계 상태는 목적이 다를 때만 별도 다이어그램으로 만든다. 같은 내용을 중복 표현하지 않는다.
- 클래스 다이어그램은 Architecture Spec 단계에서만 만든다.
- `.puml`가 유일한 편집 원본이다. SVG·PNG는 원본에서 다시 만들 수 있는 파생 산출물이다.
- 필요한 다이어그램은 원본 작성, SVG 렌더, Markdown 연결, Spec 내용과의 일치 검토를 모두 통과해야 해당 단계가 완료된다.
- 렌더 실패 시 해당 Spec 단계는 완료될 수 없다.

## 7. 상태와 전이

이 기능 자체의 업무 상태는 별도 모델링하지 않는다. 다만 대상 기능에 상태 생명주기가 있을 때 Product 또는 Architecture 관점의 상태 다이어그램을 적용한다.

## 8. 실패·예외·경계

| 상황 | 기대 결과 |
|---|---|
| 렌더 실패 | 오류를 보고하고 Spec 완료를 막는다. |
| 흐름 변경인데 다이어그램 누락 | Spec 검토에서 누락으로 처리하고 완료를 막는다. |
| 상태 표현이 Product·Architecture에서 동일 | 한 다이어그램만 유지하고 중복을 만들지 않는다. |
| 기존 Spec | 소급 마이그레이션하지 않는다. 새로 생성되는 Spec부터 적용한다. |
| PR 이미지 링크 실패 | PR 본문을 완료하지 않고 링크·미리보기를 수정한다. |

## 9. 입력과 출력

| 구분 | 내용 |
|---|---|
| 입력 | 확정된 요구사항, 유스케이스, 흐름 변경, 설계 결정, 상태 전이. |
| 원본 출력 | 티켓별 `diagrams/` 하위의 `.puml` 파일. |
| 문서 출력 | `product-spec.md`, `architecture-spec.md`, SVG 참조. |
| PR 출력 | `eli5` 방식의 한눈에 보기와 변경 다이어그램별 접기식 SVG 미리보기. |

## 10. 범위와 비목표

포함:

- 새로 생성되는 `spec-me` Spec의 단계별 다이어그램 산출물.
- PlantUML 원본 렌더와 Spec Markdown 포함.
- PR의 접기식 다이어그램 미리보기와 간결한 설명.

제외:

- 기존 `docs/specs/**`의 소급 마이그레이션.
- 모든 변경에 모든 UML 다이어그램 강제.
- 외부 PlantUML MCP 설치 또는 원격 렌더 서비스 의존.

## 11. 우선순위와 트레이드오프

1. 원본과 요구사항의 정확성·추적성.
2. 렌더 재현성과 검증 가능성.
3. PR 첫 화면의 가독성.
4. PNG는 외부 공유 또는 PR 첨부가 필요한 경우에만 생성한다. 기본 문서 이미지는 SVG다.

## 12. 수용 기준

- [ ] 새 Product Spec은 흐름 신설·변경 시 유스케이스·액티비티 PlantUML 원본과 SVG를 가진다.
- [ ] 새 Architecture Spec은 적용 가능한 클래스·설계 상태 PlantUML 원본과 SVG를 가진다.
- [ ] 상태 다이어그램은 업무 규칙과 설계 책임의 차이가 있을 때만 둘로 분리된다.
- [ ] 모든 생성 `.puml`은 렌더 가능하고, 연결된 SVG가 Markdown에서 표시된다.
- [ ] 각 다이어그램은 관련 요구사항 또는 유스케이스 ID를 식별할 수 있다.
- [ ] `gh-open-pr`는 PR 시작 부분에 `eli5` 방식 요약을 만들고, 변경 그림을 ID·이름·유형이 있는 `<details>` 블록으로 표시한다.
- [ ] PR SVG 링크는 head branch를 가리키며 GitHub 미리보기가 표시된다.
- [ ] 기존 Spec은 변경하지 않는다.
