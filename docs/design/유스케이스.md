# Use Case Document

## 1. Actor Definitions

### Main Actors

- End user.

### Supporting Actors

- None.

## 2. High-Level Use Case List

### End User

- UC-01. End user calculates an arithmetic expression.
- UC-02. End user edits the current expression.
- UC-03. End user clears the calculator state.
- UC-04. End user retries calculator use after an app failure.

## 3. Use Case Details

## UC-01. End user calculates an arithmetic expression.

**Actor**

- End user.

**Supporting Actor**

- None.

**Goal**

- Obtain a numeric result or `ERROR` for the current arithmetic expression.

**Preconditions**

- The calculator page loaded successfully.
- The current page session is active in a supported desktop browser.
- The user has entered an expression with keyboard input, on-screen buttons, or both.

**Main Flow**

1. The user enters numbers, operators, decimal points, and parentheses into the current expression.
2. The user triggers `=` or `Calculate`.
3. The system evaluates the full expression with operator precedence.
4. If evaluation succeeds, the system formats the result for display.
5. The system shows the numeric result.

**Exception Flow**

- If the expression contains an invalid operation, the system shows `ERROR`.
- If the expression is syntactically invalid or incomplete, the system shows `ERROR`.
- If the expression is invalid or incomplete, the system does not auto-correct the expression.

**Result**

- On success, the system shows the evaluated numeric result.
- On success with a long decimal output, the system shows the result using 10 decimal places.
- On failure, the system shows `ERROR`.

**Non-Functional Requirements**

- Evaluation and result display complete within 1 second after `=` or `Calculate`.
- Calculation runs entirely in browser memory without backend or third-party network calls.

## UC-02. End user edits the current expression.

**Actor**

- End user.

**Supporting Actor**

- None.

**Goal**

- Adjust the current expression before the next calculation.

**Preconditions**

- The calculator page loaded successfully.
- The current page session is active in a supported desktop browser.

**Main Flow**

1. The user enters or changes characters in the current expression by keyboard input, on-screen buttons, or both.
2. The user may trigger a single-character delete or backspace action.
3. The system updates the current expression immediately.
4. If an old result is visible and the expression changes, the system clears the old result immediately.

**Exception Flow**

- If the expression becomes invalid or incomplete during editing, the system keeps the edited expression as entered.
- If the expression becomes invalid or incomplete during editing, the system does not auto-correct the expression.

**Result**

- The system shows the updated current expression.
- Any previously shown result is cleared when the expression changes.

**Non-Functional Requirements**

- Expression updates appear immediately during normal desktop-browser interaction.
- Edited expression state stays only in browser memory for the current page session.

---

## UC-03. End user clears the calculator state.

**Actor**

- End user.

**Supporting Actor**

- None.

**Goal**

- Reset the current expression and current result.

**Preconditions**

- The calculator page loaded successfully.
- The current page session is active in a supported desktop browser.

**Main Flow**

1. The user triggers `Clear`.
2. The system removes the current expression.
3. The system removes the current result.
4. The system shows the empty calculator state.

**Exception Flow**

- None.

**Result**

- The calculator returns to an empty in-memory state for the current page session.

**Non-Functional Requirements**

- Clear action completes within normal interactive browser response time.
- Cleared state is not stored beyond the current in-memory page session.

---

## UC-04. End user retries calculator use after an app failure.

**Actor**

- End user.

**Supporting Actor**

- None.

**Goal**

- Retry access to the calculator after the app fails to load or run.

**Preconditions**

- The app failed to load or the browser could not run the calculator logic.
- The system showed a simple failure state.

**Main Flow**

1. The user sees the failure state.
2. The user refreshes the page manually.
3. The system attempts to load the calculator again.
4. If loading succeeds, the system shows the empty calculator state.

**Exception Flow**

- If the refresh attempt does not recover the app, the system shows the failure state again.

**Result**

- On success, the user can use the calculator from an empty state.
- On failure, the failure state remains and another manual refresh is required.

**Non-Functional Requirements**

- Recovery mechanism is limited to manual page refresh.
- Operational logging is limited to browser-console error logs for app-load failures and unexpected runtime exceptions.

## 4. System-Wide Non-Functional Requirements

### 4.1 Performance

- Expression evaluation and result display complete within 1 second after `=` or `Calculate` on a typical modern desktop browser.

### 4.2 Scalability

- The application is deployable as a static frontend-only web application on standard web hosting.
- No backend scaling requirement exists for v1.

### 4.3 Availability

- No explicit uptime SLA is defined for v1.
- Official client scope for v1 is desktop browsers only.

### 4.4 Data Consistency

- Calculator state exists only in browser memory for the current page session.
- No cross-user or cross-session consistency mechanism is required.

### 4.5 Concurrency Control

- No explicit concurrency target is required beyond normal static web hosting behavior.

### 4.6 Security

- The system requires no login, user accounts, or access control.
- The system makes no backend or third-party network calls during calculation.
- The system does not store user input beyond in-memory page state.

### 4.7 Failure Handling and Recovery

- App-load or runtime failure recovery requires manual page refresh.
- No offline recovery, saved-state recovery, or state restore mechanism is required for v1.

### 4.8 Auditability and Operability

- Operational logging is limited to browser-console error logs for app-load failures and unexpected runtime exceptions.
- Usage analytics are omitted.
- Diagnostic history is omitted.
