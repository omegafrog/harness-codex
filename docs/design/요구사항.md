# 요구사항 명세서

## 1. 개요
- 초기 아이디어: 웹에서 실행되는 3D 싱글 플레이 대장장이 게임 프로토타입을 만든다.
- 문제 상황: 플레이어는 AI 대장장이들이 경쟁하는 마을 시장에서 평범한 무기 판매만으로는 우위를 점하기 어렵다. 이상하고 독창적인 재료로 만든 도구와 무기의 예상 밖 쓰임을 시장에 퍼뜨려 경쟁자를 이겨야 한다.
- 목표: 플레이어가 던전에서 확보한 다양한 재료로 무기와 도구를 제작하고, 창의적 쓰임에서 발생하는 수요 급등을 이용해 마을 내 독점도 또는 시장 지배력을 높인다.
- 범위: PC 브라우저 전용, 싱글 플레이, 로컬 저장 기반의 프로토타입으로 한정한다. 필수 플레이 흐름은 `세션 시작 -> 던전 준비 및 동행 -> 재료 획득 -> 아이템 제작 -> 가판대 판매 -> 수요/독점도 변화 확인`까지 포함한다.

## 2. 액터 및 이해관계자
- 주요 액터: 플레이어
- 보조 액터: 브라우저 로컬 저장소
- 이해관계자: 게임 기획자, 프로토타입 구현자

## 3. 기능 요구사항
### 3.1 세션 및 진행 관리
- FR-001. 시스템은 플레이어가 싱글 플레이 세션을 새로 시작하거나 기존 로컬 저장 데이터를 불러와 이어서 플레이할 수 있어야 한다.
- FR-002. 시스템은 플레이어의 시장 독점도 또는 이에 준하는 경쟁 우위 지표를 세션 단위로 추적해야 한다.
- FR-003. 시스템은 프로토타입 진행에 필요한 핵심 상태를 로컬에 저장해야 한다. 저장 대상에는 최소한 재료 보유 현황, 제작품, 판매 중인 상품, 시장 수요 상태, 독점도, 해금된 던전이 포함되어야 한다.
- FR-003-1. 시스템은 상태 변경이 성공적으로 끝나는 유스케이스마다 자동 저장해야 하며, 수동 저장은 제공하지 않는다.
- FR-003-2. 시스템은 최신 저장 스냅샷과 직전 정상 저장 스냅샷을 유지해야 한다.
- FR-003-3. 자동 저장 스냅샷은 게임세션, 인벤토리, 가판대, 시장상태를 하나의 JSON 문서로 묶어 브라우저 로컬 저장소에 저장한다.

### 3.2 시장 경쟁 및 목표 달성
- FR-004. 시스템은 플레이어 외에 복수의 경쟁 AI 대장장이를 시장 참여자로 표현하고, 이들의 존재가 플레이어의 판매 기회와 독점도 변화에 영향을 주어야 한다.
- FR-004-1. 프로토타입의 경쟁 AI 대장장이는 3명이어야 한다.
- FR-005. 시스템은 플레이어의 판매 성과와 시장 반응을 바탕으로 독점도 또는 시장 지배력의 상승·하락을 계산해야 한다.
- FR-005-1. 플레이어의 독점도가 100에 도달하면 프로토타입 승리 상태로 판정해야 한다.
- FR-006. 시스템은 특정 아이템이나 특성이 유행하거나 수요가 폭증하는 상황을 표현해야 하며, 이 변화가 경쟁 우위에 반영되어야 한다.
- FR-006-1. 경쟁 AI 대장장이는 기본적으로 시장 점유율 경쟁을 수행해야 하며, 플레이어가 만든 유행 특성을 따라 하거나 카운터 상품을 시장에 내놓을 수 있어야 한다.
- FR-006-2. 경쟁 AI 대장장이는 프로토타입 범위에서 재료 수집, 던전 탐사, 모험가 동행 기능까지는 수행하지 않는다.

### 3.3 던전 탐사 및 재료 수집
- FR-007. 시스템은 플레이어가 모험가 NPC를 고용하고 던전 공략에 동행할 수 있게 해야 한다.
- FR-007-1. 프로토타입의 모험가 NPC는 개별 성장, 계약, 장비 상태를 가진 엔티티로 관리하지 않고, 던전 탐사에 사용할 동행 구성 값으로만 표현한다.
- FR-008. 시스템은 던전별로 획득 가능한 재료, 예상되는 위협, 선호되는 도구 또는 무기 특성을 다르게 구성해야 한다.
- FR-008-1. 프로토타입은 최소 3개의 던전을 제공해야 한다.
- FR-009. 시스템은 기본 재료뿐 아니라 기괴하거나 비정상적인 재료를 획득 대상으로 제공해야 한다.
- FR-009-1. 프로토타입은 최소 20종의 재료를 제공해야 한다.
- FR-010. 시스템은 각 재료에 강도, 경도, 길이 영향, 냄새, 유기성, 희귀성, 기괴함 같은 속성 또는 특성 데이터를 부여할 수 있어야 한다.
- FR-011. 시스템은 던전 경험을 통해 플레이어가 어떤 특성의 도구나 무기가 특정 상황에 유리한지 자연스럽게 이해할 수 있는 단서를 제공해야 한다.
- FR-011-1. 던전 공략 실패 시 기존 보유 재료는 잃지 않으며, 해당 탐사의 보상은 기본 보상 수량의 50%로 축소되고 희귀 재료와 특성 단서는 지급되지 않는다.
- FR-011-2. 프로토타입에서는 인벤토리와 재료 보유 한도를 두지 않는다.

### 3.4 제작 및 아이템 속성 생성
- FR-012. 시스템은 플레이어가 획득한 재료와 선택한 외형 또는 도구 형태를 조합해 무기나 도구를 제작할 수 있게 해야 한다.
- FR-012-1. 프로토타입은 최소 6종의 아이템 형태를 제공해야 한다.
- FR-013. 시스템은 상세한 수동 단조 미니게임 없이도 제작 결과가 확정되는 프로토타입 흐름을 제공해야 한다.
- FR-014. 시스템은 제작 결과물에 대해 재료 특성과 외형 조합을 반영한 아이템 속성을 계산해야 한다.
- FR-015. 시스템은 제작 결과물의 본래 용도 외에도 파생 가능한 쓰임을 판단하기 위한 해석 입력값을 유지해야 한다.
- FR-015-1. 유효한 재료 조합과 아이템 형태로 제작을 확정하면 제작은 항상 성공한다.
- FR-015-2. 조합이 유효하지 않거나 재료가 부족한 경우에만 제작이 실패하며, 이 경우 재료는 소비되지 않는다.

### 3.5 창의적 쓰임 해석 및 시장 반응
- FR-016. 시스템은 아이템의 특성 조합을 바탕으로 원래 용도에서 벗어난 창의적이거나 기괴한 쓰임을 도출해야 한다.
- FR-016-1. 프로토타입의 창의적 쓰임 판단 엔진은 규칙 기반으로 후보를 생성하고, 템플릿 또는 간단한 AI풍 설명 생성 방식으로 결과 설명을 구성해야 한다.
- FR-017. 시스템은 도출된 쓰임이 말이 안 되더라도 웃기고 과장된 결과를 포함할 수 있도록 설계되어야 한다.
- FR-018. 시스템은 창의적 쓰임이 특정 던전 공략, 생활 문제 해결, 유행성 소비, 소문 확산 등에 연결되어 수요를 변화시킬 수 있어야 한다.
- FR-019. 시스템은 창의적 쓰임이 발견되었을 때 어떤 이유로 수요가 올랐는지 플레이어가 이해할 수 있는 형태로 피드백을 제공해야 한다.
- FR-019-1. 시스템은 향후 LLM 또는 외부 API를 연결해 창의적 쓰임 해석을 고도화할 수 있도록 확장 지점을 고려해야 하지만, 외부 API 의존은 프로토타입 필수 범위가 아니다.
- FR-019-2. 시스템은 창의적 쓰임 해석 결과와 수요 변화 원인을 저장 데이터에 포함해야 하며, 불러오기 시 임의로 재계산하지 않는다.

### 3.6 판매 및 시장 피드백
- FR-020. 시스템은 플레이어가 제작한 아이템을 대장간 가판대에 진열하고 판매를 기다릴 수 있게 해야 한다.
- FR-021. 시스템은 시장 수요, 아이템 특성, 창의적 쓰임, 경쟁 상황을 반영하여 판매 결과를 계산해야 한다.
- FR-021-1. 판매 완료된 제작품은 활성 인벤토리와 가판대 슬롯에서는 제거하고, 판매 이력 요약으로만 보존한다.
- FR-022. 시스템은 판매 이후 플레이어에게 판매량, 인기 원인, 경쟁 변화, 독점도 증감 결과를 보여줘야 한다.
- FR-023. 프로토타입의 가판대 판매 슬롯은 3개로 제한한다.
- FR-024. 판매 가격은 플레이어가 직접 설정하지 않고, 시스템이 아이템 속성, 수요, 경쟁 상황을 기준으로 자동 산정한다.
- FR-025. 판매 보상은 금전, 독점도 변화, 시장 피드백으로 구성하며, 평판은 프로토타입 범위에서 별도 영속 상태로 관리하지 않는다.
- FR-025-1. 프로토타입의 금전은 정수 단위 골드로만 표현하며, 판매 보상 누적 외의 지출 경제는 구현하지 않는다.

## 4. 비기능 요구사항
### 4.1 성능
- NFR-001. 시스템은 PC 브라우저에서 구동되어야 한다.
- NFR-002. 3D 표현은 고사양 사실주의보다 카툰 스타일의 깔끔한 시각 일관성을 우선해야 한다.
- NFR-003. 시스템은 PC 브라우저에서 30fps 이상을 목표로 하며, 카툰 스타일의 저폴리 3D 표현을 우선한다.
- NFR-003-1. 초기 로딩은 프로토타입 기준 5초 이내를 목표로 하고, 복잡한 실시간 물리 효과와 고사양 그림자는 사용하지 않는다.

### 4.2 동시성 제어
- NFR-004. 시스템은 싱글 플레이 전용으로 동작해야 하며, 동일 세션 내 게임 상태 변경은 단일 플레이 흐름 기준으로 순차 적용되어야 한다.
- NFR-005. 자동 저장은 상태 변경 유스케이스 완료 직후 수행하며, 같은 유스케이스에서 중복 저장 요청이 발생하면 마지막 완료 상태만 저장한다.
- NFR-005-1. 프로토타입의 BC 간 협력은 이벤트 버스나 비동기 메시징 없이 동일 프로세스 동기 호출로 처리한다.

### 4.3 데이터 정합성
- NFR-006. 재료 소비, 제작 결과 생성, 판매 결과 반영, 독점도 변경은 저장 데이터 기준으로 일관되게 적용되어야 한다.
- NFR-007. 저장 직후 다시 불러왔을 때 인벤토리, 시장 상태, 독점도 값이 손상되지 않아야 한다.
- NFR-008. 창의적 쓰임 계산 결과와 수요 변화 원인은 저장하고, 불러오기 시 재계산하지 않는다.

### 4.4 확장성
- NFR-009. 시스템은 새로운 재료, 던전, 적, 아이템 형태, 특성 조합 규칙을 추가해도 핵심 루프를 크게 수정하지 않도록 확장 가능해야 한다.
- NFR-010. 창의적 쓰임 생성 로직은 후보 규칙, 확률, 설명 텍스트를 확장할 수 있어야 한다.
- NFR-011. 콘텐츠 데이터는 던전, 재료, 아이템 형태, 경쟁자, 창의적 쓰임 규칙을 독립적으로 추가할 수 있는 구조를 전제로 한다.

### 4.5 장애 격리 및 가용성
- NFR-012. 창의적 쓰임 생성이 실패하거나 비정상 결과를 내더라도 세션 전체가 중단되지 않고 대체 결과 또는 기본 판매 로직으로 진행되어야 한다.
- NFR-013. 로컬 저장 불러오기에 실패하면 새 세션 시작 또는 마지막 정상 저장 복구 같은 대응 경로를 제공해야 한다.
- NFR-014. 브라우저 탭 새로고침 시 마지막 자동 저장 스냅샷에서 복구한다. 렌더링 리소스 누락 시 해당 에셋은 기본 카툰 placeholder로 대체한다.

### 4.6 보안
- NFR-015. 시스템은 로컬 저장 데이터를 사용하는 범위와 항목을 플레이어에게 예측 가능하게 유지해야 한다.
- NFR-016. 프로토타입은 외부 네트워크 API 또는 생성형 AI 서비스를 사용하지 않는다.
- NFR-016-1. 프로토타입은 외부 API나 LLM 연결 없이도 완전한 핵심 플레이 루프가 동작해야 한다.
- NFR-017. 로컬 저장 데이터 변조 방지는 프로토타입 범위에서 제공하지 않으며, 손상된 데이터는 복구 정책으로 처리한다.

### 4.7 장애 대응 및 복구
- NFR-018. 손상된 최신 저장 데이터가 발견되면 시스템은 직전 정상 저장 스냅샷 복구를 먼저 시도하고, 그것도 실패하면 새 게임 시작만 제공한다.
- NFR-019. 아이템 해석 로직이나 수요 계산 로직에서 예외가 발생하면 원인 확인이 가능하도록 오류 정보를 남겨야 한다.
- NFR-019-1. 자동 저장 실패 시 도메인 상태는 메모리에 유지하고, 플레이어에게 저장 실패 알림을 표시하며, 개발용 로그에 실패 원인을 기록한다.

### 4.8 감사 추적 및 운영성
- NFR-020. 프로토타입 단계에서도 판매 결과, 수요 급등 원인, 아이템 특성 해석 결과를 확인할 수 있는 디버그 가능성이 확보되어야 한다.
- NFR-021. 수요 폭증 또는 독점도 변화의 원인을 플레이어 또는 개발자가 추적할 수 있어야 한다.
- NFR-022. 플레이어에게는 판매 결과, 인기 원인, 독점도 변화만 노출하고, 개발용 디버그 로그는 별도 디버그 패널과 브라우저 콘솔에만 노출한다.
- NFR-023. 개발용 디버그 로그는 최소한 제작 속성 계산, 창의적 쓰임 후보, 수요 변화 원인, 경쟁 AI 대응, 독점도 증감 값을 포함해야 한다.
- NFR-024. 판매 피드백의 원천 데이터는 도메인 결과로 유지하되, 화면 표시용 문구와 배치는 프레젠테이션 모델에서 변환한다.
