## 4. 실패/복구/일관성 정책
|상황|정책|보상/재시도|관측성|테스트 필요성|
|---|---|---|---|---|
|Invalid or incomplete expression on explicit calculation|Return `EvaluationOutcome` failure and show `ERROR`|No retry; user edits expression manually|Optional test assertion plus no success result visible|required|
|Expression changes after result shown|Clear stale result immediately|No compensation needed|UI state assertion in tests|required|
|Clear requested|Reset expression, result, and visible state atomically to empty state|No retry needed|UI state assertion in tests|required|
|App load/runtime failure|Enter simple failure-visible state|User manually refreshes page|Browser-console error logs only|required|
|Manual refresh recovery success|Restart from empty in-memory state|No restore of old state|UI state assertion in tests|required|
|Repository adapter failure in v1|Treat as implementation defect because v1 adapter is in-memory only|Fix code; no runtime compensation policy|Test failure or runtime exception log|required|

## 5. 구현 계획 반영 사항
- Planner must preserve repository interface separation even though v1 uses only an in-memory adapter.
- Planner must not introduce backend, file persistence, Redis, messaging, analytics, or history features.
- Planner must include Vitest coverage for domain/service/UI state rules and Playwright coverage for approved UC happy/exception flows.
- Executor must not move parsing, `ERROR` decision logic, stale-result clearing, clear/reset rules, or recovery transitions out of approved domain boundaries.
- Executor must keep manual-refresh recovery and browser-console-only operational logging behavior.
