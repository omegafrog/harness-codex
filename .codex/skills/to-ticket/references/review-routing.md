# Review routing

`to-ticket` plan authoring waits with `REVIEW_REQUIRED` after writing or revising the canonical plan set. Plan review is performed by the main orchestrator with a fresh, read-only `plan_reviewer` native subagent. It is not an executor stage. Tracker publication is a separate `tracker-publish` workflow stage.

After split approval and canonical plan writing, the orchestrator creates an attempt with `harness-plan-review.mjs begin`, passes the exact admission snapshot to a fresh reviewer, validates the result against `plan-review/review-record.schema.json`, writes it to the control session, and records it with the same attempt ID. A `revise` verdict resumes the same author execution with a feedback record path. Once revisions are complete the author returns `REVIEW_REQUIRED`; the orchestrator creates a new attempt and a different reviewer. A `pass` verdict resumes the author to complete plan authoring only after `harness-plan-review.mjs check --phase planning` succeeds. The orchestrator then dispatches the separate `tracker-publish` stage through the standard stage runner; it does not call a publisher directly.

The reviewer input is the whole snapshot on the first attempt. Re-review uses `review_delta`, prior findings, and directly affected relationships; ambiguous scope requires reading the full affected document. The reviewer returns all snapshot `{path, sha256}` pairs. The record CLI converts this array into the path-to-hash map used by the review ledger and rejects a stale snapshot.

The orchestrator carries the actual execution IDs of the initial author run and every `to-ticket` feedback resume, plus the actual ID of each independent reviewer. It never treats a user answer as a review pass. After three attempts without a pass, it asks the user to resolve the concrete scope or decision. Author finalization and the publisher stage both verify the latest review against current files; tracker and Beads changes happen only in the publisher stage after the precheck passes.
