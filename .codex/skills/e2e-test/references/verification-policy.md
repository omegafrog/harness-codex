# 검증 선택과 E2E 실행 정책

이 문서는 테스트 선택을 위한 수동 의미 기준이며 런타임이 자동 판단하거나 집행하지 않는다. split plan workflow에서는 각 plan의 비즈니스 로직 단위 테스트를 plan 구현 중 작성·실행하고, 전체 split plan 구현·개별 검증·통합이 끝난 뒤 feature-level E2E를 마지막에 한 번 실행한다. `to-ticket`은 계획된 사용자 흐름, 관측 가능한 oracle, execution profile, timeout, 총 시도 budget을 plan-set test contract에 기록한다. 개별 plan 경계에서는 E2E를 실행하지 않는다. 독립 작업에서는 명시적인 E2E/full-stack/browser end-to-end 요청 또는 저비용 검사로 실패를 확인할 수 없는 승인된 critical cross-boundary 위험에 대해서만 실행한다. 일반적인 “테스트/검증해” 요청이나 서비스 실행 요청만으로 독립 작업의 E2E를 추정하지 않는다. 필요한 smoke check는 더 작은 기존 실행 profile로 수행한다. 문서·내부 리팩터링·경계를 바꾸지 않는 순수 로직은 통상 E2E `해당 없음 — 사유`다. 승인 계획과 충돌하면 실행 전에 근거 있는 수정안을 제시한다. 약속된 검증을 조용히 생략하지 않는다.

Agent 기반 서비스는 Playwright로 전송/UI의 안정된 상태를 검증한다. 예: UI stub은 제출 request와 streaming/loading→done 전이를 확인하고 응답 문구는 exact match하지 않는다. 이 stub 검증은 live agent 품질을 증명하지 않는다. 실제 live agent 검증은 trace/correlation ID로 goal, terminal state, contracted tool choice/arguments/schema, permission, persistence, side effect를 확인하고 고정된 task/environment budget 안에서 bounded async terminal-state wait를 쓴다. 예: 요구한 record가 정확히 한 번 저장되고 필수 tool args가 맞으며 금지 side effect가 없는지 본다. 완료 UI만으로 성공 처리하지 않는다. 동적 문구·비계약 순서·항목 수는 exact match하지 않는다. 명시적 canonical contract만 예외다. 답변 품질은 제한된 task/rubric 평가로 별도 다루며, evaluator는 tool/safety 실패를 덮지 않는다. 넓은 평가 suite를 자동 시작하지 않는다.

Runner는 테스트나 source를 편집하지 않는다. 첫 실행 전에 승인된 spec/rubric의 oracle과 task/environment budget을 고정한다. 실패는 product/test/environment/unknown으로 증거와 함께 분류한다. 기대값이 잘못되었다고 제안할 때는 승인 Spec의 근거를 먼저 보인다. Caller가 assertion을 고칠 때도 원래 승인 oracle을 보존하며, 관측된 출력을 만족시키려고 기준이나 Spec을 다시 쓰지 않는다. 시나리오별 시도 budget은 최초 1회와 진단 근거를 반영한 재실행 최대 1회이며, handoff 사이에도 공유하며 현재 시도와 남은 budget은 기존 checkpoint/test evidence 요약에 기록한다. 새 schema/field는 만들지 않는다. 계속 실패하거나 분류가 불확실하면 증거와 함께 중단·인계한다. 더 큰 campaign은 사용자가 명시적으로 요청할 때 해당 budget을 정한다.

E2E 실패 이력은 기존 절차대로 보존한다. Split plan workflow의 final E2E 실패는 해당 feature 경로를 재실행해 해결을 확인한다. 그 외 독립 lower-level 변경에는 무관한 E2E를 다시 실행하지 않으며, E2E 해결을 주장하지 않고 미해결 blocker로 남긴다.
