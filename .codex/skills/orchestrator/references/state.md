# 스키마와 실행 상태

`harness-native-stage.mjs launch`(또는 준비된 입력에 대한 `start`)가 stage의 정본 입력을 검증하고 그 실행의 `return.schema.json`을 생성 또는 검증한 뒤 실행을 예약한다. 서브에이전트는 schema 파일을 직접 읽고 지정된 출력 파일을 작성한다. `waiting_for_answers`이면 stage를 실행하지 않고 실제 답을 기다린다.

`harness-native-stage.mjs finish`는 출력의 JSON 형식과 schema만 먼저 검사한다. 형식 오류는 잘못된 필드 경로·규칙·기대값·실제값과 `next`를 반환하며 stage를 종료하지 않는다. 호출자는 오류를 같은 서브에이전트에 돌려 수정하게 한다. gate가 결과를 반려하면 `gate_error`는 정확한 errors·instruction과 `feedback_path`·`retry_input`을 반환한다. runner는 반려 정보를 실행의 `feedback.json`에 누적하며, 호출자는 `retry_input` 전체를 같은 작업자의 다음 입력에 포함하고 피드백 파일도 읽게 한다. 전술 설계 흐름의 마지막 stage `context-boundary`의 `completed/OK`는 이어서 `tactical-design.md` 전체에 대한 gate(`harness-domain-model-check.mjs`)를 한 번 통과해야 하며, 통과하지 못하면 `gate_error`와 발견 사항(각각 문제 있는 구성요소를 맡은 stage인 `owner_stage` 포함)을 반환하고 commit·기록 없이 stage를 `running`으로 둔다. 호출자는 이를 형식 오류처럼 같은 서브에이전트에 돌려 고치게 하되, `owner_stage`가 앞 stage이면 서브에이전트가 `blocked` / `DEPENDENCY_INCOMPLETE`로 그 stage를 가리키게 한다. 현재 양식에는 각 전술 stage가 소유한 부분을 완료 전에 검사하는 gate도 적용한다. 같은 검사가 상태 기록 경로에도 적용된다. 성공하면 정본 결과와 상태를 기록한다. 실행 ID, worktree, 안전한 파일 경로와 실제 승인 등 신뢰 경계는 별도로 유지한다. 실제 서브에이전트 실패는 `fail`로 기록한다. 상태 파일을 직접 수정하지 않는다.

`blocked` / `DEPENDENCY_INCOMPLETE`가 앞 stage를 `owner_stage`로 가리키면 `harness-prepare-input.mjs`(또는 `launch`)의 `--reopen-for <blocked execution_id>`가 그 stage를 되돌리지 않고 다시 연다. 이때 `state.json`의 owner 뒤 `completed` stage와 block된 stage 항목에 `stale: { owner_stage, blocked_stage, reopened_for, rerun_order, marked_at }`가 기록된다. stale 항목은 `completed/OK`여도 순서 guard(`isCurrentStage`)와 `tracker-publish` 승인·workflow 완료가 유효한 결과로 인정하지 않으며, 그 stage가 새 실행을 시작하면 표시가 지워진다. 문서·코드는 되돌리지 않는다. 절차는 [상위 stage 되돌아가기](dispatch.md#상위-stage-되돌아가기)를 따른다.
