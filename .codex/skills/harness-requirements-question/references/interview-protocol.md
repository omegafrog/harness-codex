# Requirements Interview Protocol

## 완료 조건

다음 영역을 결정 트리로 점검한다. 사용자 입력과 저장소 근거만으로 명확한 영역은 질문하지 않는다.

1. 해결할 문제와 기대 결과
2. 행위자, 이해관계자, 사용 맥락
3. 포함 범위와 제외 범위
4. 정상 시나리오와 사업 규칙
5. 실패, 거부, 예외, 경계 조건
6. 측정 가능한 성공 기준과 acceptance signal
7. 측정 가능한 비기능 요구사항

각 영역의 결과를 바꿀 수 있는 사용자 결정이 모두 해소되고 사용자가 요약에 동의해야 인터뷰가 완료된다.

## 질문 선택

- 저장소, 기존 ChangeSet 문서, 확정된 프로젝트 정책에서 찾을 수 있는 사실은 먼저 조사한다.
- 사실 확인이 아니라 제품·사업·운영 판단만 사용자에게 묻는다.
- 상위 결정이 하위 선택지를 없애면 상위 결정을 먼저 묻는다.
- 서로 독립적인 결정을 한 질문에 합치지 않는다.
- 목표나 범위를 실질적으로 바꾸지 않는 선호는 blocker로 만들지 않는다.
- 구현 전략, 상세 용어, alias, Aggregate, Event, 상태 전이는 묻지 않는다.

## 질문 형식

질문은 한국어로 한 번에 하나만 작성한다.

```markdown
### RQ-<연속 번호> — <결정 제목>

**왜 지금 결정해야 하나요?**
<초기 요청·기존 문서·조사 결과에 근거한 맥락과, 미결정 시 달라지는 요구사항>

**질문**
<행위자·상황·경계 조건을 포함한 하나의 구체적인 판단 질문>

**선택지**
- A. <서로 배타적인 선택과 영향>
- B. <서로 배타적인 선택과 영향>
- C. <필요한 경우에만 세 번째 선택과 영향>

**추천**
<A/B/C 중 하나> — <현재 목표와 제약에 비추어 추천하는 이유>

선택지의 문자 또는 원하는 정책을 직접 답해주세요.
```

- 선택지는 가능한 경우 2개, 실제로 제3의 정책이 있을 때만 3개를 제시한다.
- 추천은 중립적인 요약이 아니라 현재 근거에 따른 한 가지 답이어야 한다.
- 안전, 비용, 일정, 사용자 경험, 운영 복잡도 중 실제 trade-off를 드러낸다.
- 자유 답변이 가능하다고 명시하되, 사용자가 질문을 다시 설계하게 만들지 않는다.

## 응답 처리

- 답이 구체적이면 결정과 근거를 유지하고 다음 미확정 분기로 이동한다.
- 답이 모호하거나 조건부이면 새 질문으로 세지 않고 같은 ID에 하위 번호를 붙여 다시 묻는다. 예: `RQ-2.1`.
- 사용자가 결정을 보류하면 추천안을 기본값으로 확정해도 되는지 같은 ID로 확인한다.
- 모든 분기가 해소되면 확정된 결정과 제외 범위를 짧게 요약하고, 이 이해를 기준으로 요구사항 문서를 작성해도 되는지 마지막 단일 질문으로 확인한다.
