# Harness Requirements And Use Cases

## Purpose

이 스킬은 사용자의 초기 아이디어를 ticketon-ddd 방식의 요구사항 정의와
유스케이스 정의에 맞는 요구사항 명세서와 유스케이스 문서로 발전시킨다.

스킬이 호출되면 `.codex/agents/harness_requirements_usecases.toml`에 정의된 전담
에이전트에게 아래 작업을 맡긴다. 이 에이전트를 찾을 수 없거나 실행할 수 없으면
대체 실행하지 말고, 이유를 설명한 뒤 멈춘다.

## Embedded Standards

이 스킬은 repo의 외부 블로그 파일에 의존하지 않는다. 아래 기준을 instruction의
source of truth로 사용한다.

### 요구사항 기준

- 요구사항은 시스템이 만족해야 하는 목표와 제약을 정의한다.
- 요구사항은 기능 요구사항과 비기능 요구사항으로 분리한다.
- 기능 요구사항은 액터가 시스템을 통해 수행해야 하는 기능을 도메인/기능 그룹별로
  정리한다.
- 비기능 요구사항은 시스템의 품질 속성과 운영 제약을 정의한다.
- 비기능 요구사항은 성능, 동시성 제어, 데이터 정합성, 확장성, 장애 격리/가용성,
  보안, 장애 대응/복구, 감사 추적/운영성 관점에서 누락을 확인한다.
- 트래픽, 응답 시간, 동시 요청, 데이터 일관성, 장애 시 처리처럼 수치나 조건이
  중요한 항목은 가능한 한 측정 가능한 형태로 쓴다. 모르면 `확인 필요`로 남긴다.
- 비기능 요구사항은 에이전트가 임의로 확정하지 않는다. 사용자가 명시하지 않은
  비기능 요구사항은 `후보` 또는 `확인 필요`로 표시하고, 성능/저장/장애/보안/운영성
  질문을 통해 사용자의 의사결정을 받아 확정한다.
- 미결정 사항은 `비즈니스 정책 확인 필요`와 `기술 결정 확인 필요`로 분리한다.
- 비즈니스 정책은 성공/실패 결과, 상태 전이, 검증 규칙, 보상/손실, 가격/판매,
  인벤토리/슬롯, 시장/경쟁, 권한, 사용자에게 보이는 행동이다.
- 기술 결정은 구현 스택, 저장 방식, 렌더링/런타임, 트랜잭션/일관성, 통합 방식,
  장애 복구, 성능 목표, 로깅/디버깅, 외부 API 사용 여부다.
- 구현 스택은 요구사항 단계에서 반드시 질문한다. 최소한 클라이언트 프레임워크,
  언어, 빌드 도구, 3D/렌더링 라이브러리, 테스트 도구, 저장소/런타임 제약을
  확인하고, 사용자가 모르면 `기술 결정 확인 필요`에 남긴다.
- 이벤트 스토밍으로 넘기기 전에는 비즈니스 정책 확인 필요가 없어야 한다.

### 유스케이스 기준

- 유스케이스는 시스템 외부의 액터 관점에서 누가, 어떤 목표로, 시스템에 무엇을
  기대하는지를 작성한다.
- 요구사항은 시스템이 달성해야 하는 목표를 중심으로 설명하고, 유스케이스는 그
  목표를 사용자가 어떻게 달성하는지의 시나리오를 중심으로 설명한다.
- 시스템 내부 서버나 내부 API 간 상호작용은 유스케이스로 정의하지 않는다.
- 상위 유스케이스는 사용자 목표를 명확히 보여주는 목록이고, 상세 유스케이스는
  목표 달성을 위한 절차, 예외, 결과, 관련 비기능 요구사항을 기록한다.
- 유스케이스 이름은 `UC-01. 액터가 목표를 수행한다` 형식으로 작성한다.
- 유스케이스는 반드시 하나의 사용자 목표만 가진다. 둘 이상의 목표가 결합된 경우
  별도 유스케이스로 분리한다. 예: `회원이 대기열에 진입하고 자신의 대기열 순번을
  조회한다`는 `회원이 대기열에 진입한다`와 `회원이 자신의 대기열 순번을 조회한다`로
  분리한다.
- 유스케이스 상세 흐름에서 이벤트 스토밍 요소를 암시하거나 초안으로 추출할 때 각
  요소는 하나의 의미만 가져야 한다. 예: `이메일이 중복되지 않고 입력 형식이 유효한
  경우`는 `이메일 중복을 검증하라`와 `입력 형식 유효성을 검증하라`로 분리한다.
- 정책과 커맨드를 섞지 않는다. 예: `인증 정보가 유효하면 인증을 완료한다`는
  `인증 정보가 유효한 경우` 정책과 `인증을 완료하라` 커맨드로 분리한다.
- 커맨드는 명령형으로 작성한다.
- 이벤트는 과거형으로 작성한다.
- 정책은 조건 또는 판단 기준으로 작성한다. 예: `이메일이 사용 가능한 경우`,
  `결제가 승인된 경우`.
- 위 조건을 모두 만족하지 못한 유스케이스는 완료된 것으로 간주하지 않는다.

## Invocation

사용자가 `$harness-requirements-usecases`와 함께 "~하고 싶어" 수준의 아이디어를
주면, 그 호출은 새 요구사항/유스케이스 도출 에이전트 실행 요청으로 간주한다.

전담 에이전트:

- agent id: `harness_requirements_usecases`
- config: `.codex/agents/harness_requirements_usecases.toml`
- output files:
  - `docs/design/요구사항.md`
  - `docs/design/유스케이스.md`

실행 규칙:

- 전담 에이전트를 찾을 수 없거나 실행할 수 없으면 현재 에이전트가 대신 수행하지 않는다.
- 실패 이유를 사용자에게 설명하고 멈춘다.
- 전담 에이전트는 코드, 설정, 스킬 파일을 수정하지 않는다.
- 전담 에이전트의 쓰기 범위는 `docs/design/요구사항.md`와
  `docs/design/유스케이스.md`로만 제한한다.

```text
너는 harness 요구사항/유스케이스 도출 에이전트다.

사용자의 초기 아이디어를 바탕으로 지속적으로 질문하면서 요구사항과 유스케이스를 도출한다.
스킬에 내장된 ticketon-ddd 방식의 요구사항/유스케이스 기준과 템플릿을 따른다.
외부 블로그 파일이나 repo-local 참고 문서에 런타임 의존성을 두지 않는다.

소유 파일:
- docs/design/요구사항.md
- docs/design/유스케이스.md

규칙:
- 기존 사용자 변경을 되돌리지 않는다.
- 코드, 설정, 스킬 파일을 수정하지 않는다.
- 충분히 명확하지 않은 부분은 추정하지 말고 질문한다.
- 비기능 요구사항은 임의로 확정하지 않는다. 사용자가 말하지 않은 품질 속성은 후보로만 적고 확인 질문을 남긴다.
- 구현 스택은 요구사항 단계에서 반드시 질문한다. 사용자가 모르면 확정하지 말고 `기술 결정 확인 필요`에 남긴다.
- 질문은 한 번에 3-7개 이내로 묶고, 사용자가 답하면 문서를 갱신한다.
- 요구사항은 기능 요구사항과 비기능 요구사항을 분리한다.
- 유스케이스는 시스템 외부 액터의 목표 중심으로만 작성한다.
- 내부 서버/API 간 흐름은 유스케이스로 만들지 않는다.
- 모든 유스케이스는 지정된 템플릿을 따른다.
- 유스케이스는 하나의 사용자 목표만 가져야 하며, 복합 목표는 별도 유스케이스로 분리한다.
- 이벤트 스토밍 요소를 암시하거나 초안으로 추출할 때 커맨드, 이벤트, 정책은 각각 하나의 의미만 가져야 한다.
- 정책과 커맨드를 섞지 않는다. 커맨드는 명령형, 이벤트는 과거형, 정책은 조건 또는 판단 기준으로 작성한다.
- 이 조건을 모두 만족하지 못한 유스케이스는 완료로 표시하지 말고 확인 필요 또는 분리 필요로 남긴다.
- 산출물은 docs/design/요구사항.md 와 docs/design/유스케이스.md 단일 파일에만 작성하거나 업데이트한다.
- 전담 에이전트를 찾을 수 없거나 실행할 수 없으면 이유를 설명하고 멈춘다.
```

## Workflow

1. **기준 확인**
   이 스킬의 `Embedded Standards`, `Requirements Document Template`,
   `Use Case Document Template`을 이번 작업의 기준으로 삼는다.

2. **초기 아이디어 정리**
   사용자의 한두 문장 아이디어를 문제 상황, 목표 사용자, 기대 결과, 핵심 제약으로
   나누어 임시로 정리한다.

3. **질문 루프**
   요구사항과 유스케이스를 작성할 만큼 명확해질 때까지 질문한다. 한 번에 너무 많은
   질문을 하지 말고 3-7개만 묻는다. 질문은 액터, 목표, 주요 기능, 실패/예외,
   구현 스택, 비기능 요구사항, 권한/보안, 외부 시스템, 운영 제약을 우선한다.
   구현 스택 질문에는 최소한 클라이언트 프레임워크, 언어, 빌드 도구,
   3D/렌더링 라이브러리, 테스트 도구, 저장소/런타임 제약을 포함한다.
   비기능 요구사항에 대해서는 최소한 성능 목표, 저장/정합성, 장애 복구, 보안,
   운영/디버깅 필요성을 확인한다.

4. **요구사항 도출**
   기능 요구사항은 사용자가 시스템으로 달성하려는 기능 목표로 작성한다. 비기능
   요구사항은 성능, 동시성, 정합성, 확장성, 장애 격리, 보안, 복구, 감사/운영성으로
   분류한다. 사용자가 확정하지 않은 항목은 확정 요구사항처럼 쓰지 말고
   `후보` 또는 `확인 필요`로 표시한다.

5. **유스케이스 도출**
   상위 유스케이스 목록을 먼저 만들고, 각 유스케이스를 아래 템플릿에 맞게 상세화한다.
   유스케이스 이름은 `UC-01. 액터가 목표를 수행한다` 형식을 사용한다.
   하나의 유스케이스가 둘 이상의 사용자 목표를 담으면 완료하지 말고 별도 유스케이스로
   분리한다. 상세 흐름이나 이벤트 스토밍 준비 메모에서 커맨드, 이벤트, 정책을 암시하는
   문장은 하나의 의미만 갖도록 분리하고, 정책과 커맨드를 섞지 않는다.
   커맨드는 명령형, 이벤트는 과거형, 정책은 조건 또는 판단 기준으로 작성한다.

6. **문서 작성**
   `docs/design/요구사항.md`와 `docs/design/유스케이스.md`를 생성하거나 업데이트한다.
   기존 내용이 있으면 무조건 덮어쓰지 말고 현재 아이디어와 관련된 섹션을 갱신한다.

7. **완료 기준 확인**
   문서에 미정 항목이 남아 있으면 마지막에 `확인 필요` 섹션으로 모아 다음 질문을 남긴다.
   문서가 충분하면 산출물 경로와 남은 리스크만 짧게 보고한다.
   단, 비즈니스 정책 미결정이 남아 있으면 이벤트 스토밍 준비 완료로 보고하지 않는다.
   모든 유스케이스가 하나의 사용자 목표만 갖고, 이벤트 스토밍 요소 후보가 하나의 의미만
   가지며, 정책/커맨드가 분리되어 있고, 커맨드/이벤트/정책의 문장 형식이 각각
   명령형/과거형/조건 또는 판단 기준을 만족할 때만 유스케이스 완료로 보고한다.

## Use Case Document Template

`docs/design/유스케이스.md`는 다음 구조를 따른다.

```markdown
# 유스케이스 문서

## 1. 액터 정의
### 주요 액터
- ...

### 보조 액터
- ...

## 2. 상위 유스케이스 목록
### <액터 그룹>
- UC-01. ...

## 3. 유스케이스 상세
```

## Question Checklist

질문은 다음 누락 정보를 채우기 위한 것이다.

- 누가 시스템을 사용하는가? 주요 액터와 보조 액터는 누구인가?
- 각 액터가 달성하려는 목표는 무엇인가?
- 반드시 제공해야 하는 기능은 무엇인가?
- 성공 결과와 실패 결과는 어떻게 구분되는가?
- 권한, 인증, 개인정보, 감사 추적이 필요한가?
- 외부 시스템이나 결제/알림/인증 같은 보조 액터가 있는가?
- 트래픽, 응답 시간, 동시성, 정합성 요구가 있는가?
- 장애가 발생했을 때 격리, 재시도, 보상 처리가 필요한가?
- 이번 문서의 범위 밖으로 둬야 할 것은 무엇인가?
