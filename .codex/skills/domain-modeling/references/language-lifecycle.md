# 현행 용어와 폐기 기록

새 Spec·설계·코드·계획의 용어는 영향받는 Context의 현행 `CONTEXT.md` 또는 연결된 context glossary로 확인한다. 과거 Spec·ADR·구형 코드의 명칭은 역사적 근거이며, 현재 승인된 대체 관계를 되돌리는 근거가 아니다. 용어가 비슷해도 Context의 의미가 다르면 일괄 치환하지 않는다.

## 설계 중 능동적인 용어 재검토

사용자의 rename/폐기 요청을 기다리지 않는다. Product와 Architecture 설계자는 영향받는 개념의 **기존 정의와 이번에 정한 의미·책임·identity·lifecycle·Context**를 비교한다. 같은 이름이 다른 개념을 가리키거나, 같은 개념이 여러 이름으로 흩어지거나, 분리/통합·책임 이전·상태 변화로 기존 정의가 더 이상 맞지 않으면 용어 변경 후보로 다룬다. 새 기능 이름마다 새 용어를 만들거나 단순한 문체 선호로 기존 이름을 바꾸지는 않는다.

1. 기존 용어/정의, 달라진 의미와 근거, 영향 Context/문서/모델, 유지·정의 수정·rename·분리/통합·폐기 중 적절한 처리와 이유를 기존 설계 기록에 짧게 남긴다. `CONTEXT.md`에 이미 폐기 표시가 없어도 의미 불일치를 감지해야 한다.
2. 의미와 소유권이 이미 확정되어 있고 단일 현행 용어로의 정리나 정의 보정만 필요한 경우 직접 반영한다. 근거로 확정된 설계 결정을 연결하며 별도의 “이 용어를 폐기할까요?” 승인을 추가하지 않는다. 모델 변경을 확정했으면 그에 필연적으로 따르는 명칭·정의 변경도 함께 수행한다.
3. 바꾸는 이름이 업무 의미·경계·규칙까지 선택하게 하거나 현행 승인 제약과 충돌하면 관련 설계 topic을 `PARTIAL`/`UNRESOLVED`로 두고 **모델 차이와 권장 용어를 먼저 제안**한다. 기존 설계 질문 안에서 의미 결정을 해결하고, 모델의 미확정을 단순 이름 선택으로 숨기지 않는다. 의심만으로 현행 glossary를 덮어쓰거나 폐기를 확정하지 않는다.
4. 확정된 처리는 해당 소비자 프로젝트의 glossary에 즉시 반영한다. rename/폐기에는 옛 이름의 scoped 폐기→대체 기록을 남기고, 의미만 보정했다면 같은 이름의 정의를 갱신한다. Context별로 뜻이 다른 합법적 동음이의어는 scope로 구분한다. 관련 모델/Spec/다이어그램 참조와 계획의 호출자 이전·호환 예외에도 전달한다.

개념을 분리/통합한 경우에도 사라진 옛 의미의 scope와 새 개념들로의 대응을 glossary의 폐기 기록에 남긴다. 같은 문자열이 한 Context의 현행 명칭으로 남더라도 과거의 혼합 의미가 계속 유효한 것은 아니다. 현행 scoped term 자체를 잘못 폐기하거나 설계 노트만을 대체 기록으로 삼지 않는다.

Product의 문서 한정 조사와 Architecture의 source 조사를 구분한다. stage 완료 전에 영향받는 용어의 `유지 / 정의 수정 / 대체·폐기 / 미해결` 처리와 실제 glossary diff가 일치하는지 확인한다. 변경 근거가 없으면 기존 용어를 유지하며, 미해결 의미 변경이 있으면 해당 설계 topic을 완료로 처리하지 않는다. 별도의 용어 보고서나 전역 inventory는 만들지 않는다.

## 확정 변경의 기록

기존 glossary 형식을 유지하고 아래의 작은 `폐기 용어` 표를 재사용하거나 추가한다. 폐기 사실을 지우면 다음 세션이 과거 명칭을 다시 발견하므로 tombstone을 남긴다. 실제 승인된 변경만 기록하고 폐기 용어를 추측해 만들지 않는다.

| 폐기 용어 | Context / 의미 | 현행 대체어 또는 제거 | 승인 근거 | 허용되는 호환 사용 / 제거 조건 |
|---|---|---|---|---|

- 폐기 용어를 현행 canonical term이나 alias로 함께 등록하지 않는다. 새 명칭과 기존 canonical/alias/forbidden/폐기 기록을 대조하고, 충돌이 남으면 확정하지 않는다.
- 같은 범위의 현행 승인 용어와 과거 자료가 충돌하면 현행 대체 관계를 따른다. 현행 문서끼리 충돌하거나 승인 여부가 불명확하면 임의로 더 최근 파일을 고르지 말고 충돌과 필요한 결정을 보고한다.
- 기존 API/JSON key/CLI option/저장 데이터의 호환 식별자는 필요한 경계에서만 유지할 수 있다. 실제 소비자와 호환 필요성, 내부 현행 모델로의 변환, 제거 조건을 명시한다. 모든 문자열을 바꾸거나 새 도메인 타입에 구형 이름을 확산하지 않는다.
- historical Spec, migration 이력, 폐기 기록, legacy 거부 테스트, 명시적인 호환 mapping에 옛 이름이 있는 것은 부활이 아니다. 현행 설명·새 코드의 업무 명칭과 구분해 리뷰한다. 전역 문자열 금지 검사로 이 구분을 대체하지 않는다.

## 단계별 확인

Product 단계는 허용된 glossary/제품 문서로 용어만 확인하고 source/test를 읽지 않는다. Architecture/code-research는 기존 식별자와 계약의 호환 사용을 확인한다. planning은 용어 변경 범위와 예외·호출자 이전을 기존 scope/acceptance/test-contract에 연결한다. implement와 Spec review는 새 식별자·문서 및 변경 경로에서 폐기어 재도입을 확인한다.

이미 승인된 대체 관계를 적용하는 데 같은 질문을 반복하지 않는다. 새로운 폐기·의미 변경 결정은 기존 `domain-modeling` 승인/근거 흐름을 따른다. 문서에 이 표가 없으면 기존 canonical/forbidden 기록과 승인 근거부터 사용하고 빈 표를 채우기 위해 새 용어를 만들지 않는다.
