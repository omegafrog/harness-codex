# stakeholder-analysis.md 템플릿

`docs/specs/<plan-set-id>/stakeholder-analysis.md`를 아래 형식으로 쓴다. 이 문서는 persona 기록(참여자, 후보 요구사항과 결정, 충돌, 요청 범위 밖 관찰)만 담는다. 사용자가 확정한 요구사항의 초안은 `requirements.md`에 쓰며 그 모양은 [requirements.md 템플릿](../../requirements-fix/references/template.md)이 정한다. 사람이 읽는 문서이므로 한국어로 쓰고 ID, JSON 키, 경로, CLI 명령은 원형을 유지한다. 해당 사항이 없는 절에는 `없음`과 이유를 적는다.

작성 규칙:

- 후보 요구사항은 `CAND-01…`로 번호를 매기고 요청 앵커를 요청 원문에서 그대로 인용한다. 결정 전에는 `결정`을 `대기`로 둔다.
- `종류`는 persona의 `kind`를 옮긴다: `goal` 목표, `rule` 업무 규칙, `exception` 예외, `completion` 완료 조건, `actor` 행위자.
- `결정 출처`에는 결정을 준 사용자 답변의 `question_id`(`answers.json` 기준)를 적는다. 사용자가 선택지 대신 직접 쓴 문장은 `사용자 문구`로 표시하고 `내용`에 그 문장을 옮긴다. 에이전트 판단을 결정 출처로 쓰지 않는다.
- 요청이 이미 말한 범위를 되풀이하는 항목은 후보 표에 넣지 않는다. 그 범위는 `requirements.md`의 `업무 목적`에 근거 `요청 원문`으로 직접 쓴다.
- `requirements.md`의 `요구사항 초안`에는 `채택`한 후보, 확정한 업무 주체, 요청 원문이 말한 범위만 쓰고, 문장마다 근거 `CAND-xx`(요청 범위는 `요청 원문`)를 붙인다. `기각`·`보류`·`대기` 후보와 `요청 범위 밖 관찰`은 쓰지 않는다.
- 업무 주체 초안은 사용자가 확인하기 전까지 `requirements.md`에 출처 `요청 해석(에이전트 제안)`으로 두고, 확인하면 출처를 그 `question_id`로 바꾼다. 사용자가 고친 부분은 사용자 문구로 쓴다.
- `event-storming`이 낸 범위 밖 관찰은 이 문서의 `요청 범위 밖 관찰` 표에 제안자 `LENS-DOMAIN (event-storming)`, 요청 앵커 `-`로 더한다.
- 참여자 표에는 요청자 `REQUESTER`를 항상 넣는다. `### 요청 기능` 표에는 요청이 이름을 말한 기능을 모두 요청 원문 그대로 인용해 결정 `확정`, 출처 `요청 원문`으로 적는다. 요청 기능은 채택·기각·보류를 묻지 않고, 내용이 정해지지 않은 기능의 내용 질문 ID만 `내용 질문`에 적는다.
- 요청 범위 밖 관찰 표에는 요청 앵커가 원문에 없는 관찰만 둔다. 요청 앵커가 원문에 있고 아이디어가 선택 확장이면 `요청 행동과 결정` 표에 `종류: 선택 확장 관찰`, `결정: 관찰`, `근거/answer ID: 요청 앵커 "…"`, `BIZ: 해당 없음`으로 기록한다. 앵커만으로 포함 결정이 되지 않는다.

````markdown
# Stakeholder 분석

- plan set: `<plan-set-id>`
- 상태: 결정 대기 | 확정

## 1. 요청 원문

> 사용자의 요청을 수정·요약 없이 그대로 옮긴다.

## 2. 판정

- 판정: 실행 | 생략
- 사유: 판정 이유 한두 문장.
- 근거: 생략이면 요청이 바꾸는 기존 승인 Spec 경로와 업무 단위, 새 행위자·권한이 없다는 확인, 충돌하지 않는 기존 규칙.

## 3. 참여자

| ID | 구분 | 역할 | 실행 | 선택 근거 |
|---|---|---|---|---|
| REQUESTER | 요청자 | 요청자 | 요청 원문 | 요청에 적은 기능은 요청자가 이미 정한 요구사항이다 |
| LENS-DOMAIN | 전문가 관점 | 도메인 전문가 | 실행 | 기본 관점 |
| LENS-SECURITY | 전문가 관점 | 보안 전문가 | 실행 | 기본 관점 |
| SH-01 | stakeholder | 역할 이름 | 실행 | 요청 문구 "…"가 이 카드의 목표 "…"와 닿는다 |
| SH-02 | 제약 출처 | 이름 | 제약 전달 | persona로 실행하지 않고 제약을 모든 persona에 전달했다 |
| SH-03 | stakeholder | 역할 이름 | 미선택 | 요청과 닿는 문구가 없다 / 상한 3을 넘어 제외했다 / 카드 형식 오류: 오류 메시지 |

### 요청 기능

요청이 이름을 말한 최상위 기능은 요청자(`REQUESTER`)가 정한 요구사항이다. 포함 여부를 묻지 않는다. 필요한 범위 질문은 독립적으로 끝나는 행동 단위로만 한다.

| 요청 기능 | 요청 문구 | 제안자 | 결정 | 출처 | 내용 질문 |
|---|---|---|---|---|---|
| 커뮤니티 | "커뮤니티 기능" | REQUESTER | 확정 | 요청 원문 | - |

### 요청 행동과 결정

행동을 안정 ID `ACT-xx`로 기록한다. 필수 업무 행동과 필요한 파생 행동을 구분하고, 선택적 확장/무차별 CRUD를 필수로 제안하지 않는다. 포함은 BIZ 연결, 제외·후속은 근거와 결정을 남긴다. 후속은 이 workflow 뒤를 뜻한다.

| ACT | 요청 기능 | 행위자 | 행동 | 종류 | 결정 | 근거/answer ID | BIZ |
|---|---|---|---|---|---|---|---|
| ACT-01 | 커뮤니티 | 회원 | 게시글을 작성한다 | 명시 | 포함 | 요청 원문 | BIZ-01 |
| ACT-02 | 커뮤니티 | 작성자 | 게시글을 삭제한다 | 필요한 파생 | 대기 | - | - |
| ACT-03 | 커뮤니티 | 회원 | 게시글을 추천한다 | 선택 확장 관찰 | 관찰 | 요청 앵커 "커뮤니티 기능" | 해당 없음 |

## 4. 후보 요구사항

| CAND | 제안자 | 종류 | 내용 | 요청 앵커 | 근거 | 결정 | 결정 출처 |
|---|---|---|---|---|---|---|---|
| CAND-01 | LENS-DOMAIN, SH-01 | 업무 규칙 | persona가 낸 문장 | "요청 원문 인용" | persona의 근거 | 채택 | `<execution_id>:1` |
| CAND-02 | LENS-SECURITY | 예외 | … | "…" | … | 기각 | `<execution_id>:2` |
| CAND-03 | SH-01 | 목표 | … | "…" | … | 대기 | |

## 5. 충돌

| 충돌 | 요청 앵커 | 입장 | 라운드 2 결과 | 결정 | 결정 출처 |
|---|---|---|---|---|---|
| CONF-01 | "요청 원문 인용" | CAND-03 대 CAND-05 | CAND-03 제안자: keep. CAND-05 제안자: concede | CAND-03 채택, CAND-05 기각 | `<execution_id>:6` |

충돌이 없으면 `없음`으로 쓴다.

<details>
<summary>요청 범위 밖 관찰 (참고용, 요구사항 아님)</summary>

요청 앵커가 요청 원문에 없는 참고 관찰만 기록한다. 요청 앵커가 원문에 있는 선택 확장은 이 표가 아니라 요청 행동 표에 `관찰`로 기록하고 사용자 결정 없이 포함하지 않는다.

| 제안자 | 관찰 | 요청 앵커 | 근거 |
|---|---|---|---|
| LENS-DOMAIN | 결제 기능 아이디어 | "결제 기능" | 요청에 없는 선택 기능 관찰; 범위 밖 참고만 함 |

</details>
````

## 생략 판정의 문서

`판정: 생략`이면 1절과 2절만 채우고 3~5절은 `해당 없음 — 생략 판정`으로 쓴다. 근거에는 확인한 기존 Spec 경로를 적는다. 이 plan set에서는 `requirements.md`를 만들지 않고, 뒤따르는 requirements stage들은 생략을 결과 요약에 기록하고 문서를 쓰지 않는다.
