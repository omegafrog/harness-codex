# stakeholder-analysis.md 템플릿

`docs/specs/<plan-set-id>/stakeholder-analysis.md`를 아래 형식으로 쓴다. 사람이 읽는 문서이므로 한국어로 쓰고 ID, JSON 키, 경로, CLI 명령은 원형을 유지한다. 해당 사항이 없는 절에는 `없음`과 이유를 적는다.

작성 규칙:

- 후보 요구사항은 `CAND-01…`로 번호를 매기고 요청 앵커를 요청 원문에서 그대로 인용한다. 결정 전에는 `결정`을 `대기`로 둔다.
- `종류`는 persona의 `kind`를 옮긴다: `goal` 목표, `rule` 업무 규칙, `exception` 예외, `completion` 완료 조건, `actor` 행위자.
- `결정 출처`에는 결정을 준 사용자 답변의 `question_id`(`answers.json` 기준)를 적는다. 사용자가 선택지 대신 직접 쓴 문장은 `사용자 문구`로 표시하고 `내용`에 그 문장을 옮긴다. 에이전트 판단을 결정 출처로 쓰지 않는다.
- 요청이 이미 말한 범위를 되풀이하는 항목은 후보 표에 넣지 않는다. 그 범위는 `7.1 업무 목적`에 근거 `요청 원문`으로 직접 쓴다.
- `요구사항 초안`은 `채택`한 후보, 확정한 업무 주체, 요청 원문이 말한 범위만 쓰고, 문장마다 근거 `CAND-xx`(업무 목적의 요청 범위는 `요청 원문`)를 붙인다. `기각`·`보류`·`대기` 후보와 `요청 범위 밖 관찰`은 쓰지 않는다.
- 항목 상태는 `draft`(에이전트 제안), `confirmed`(사용자 확정)만 쓴다. `fixed`는 명세를 확정하는 단계가 정한다.

````markdown
# Stakeholder 분석

- plan set: `<plan-set-id>`
- 상태: 결정 대기 | 확정

## 1. 요청 원문

> 사용자의 요청을 수정·요약 없이 그대로 옮긴다.

## 2. 판정

- 판정: 실행 | 생략
- 사유: 판정 이유 한두 문장.
- 근거: 생략이면 요청이 바꾸는 기존 승인 Spec 경로와 업무 단위, 새 행위자·권한이 없다는 확인, 충돌하지 않는 기존 규칙.

## 3. 참여자

| ID | 구분 | 역할 | 실행 | 선택 근거 |
|---|---|---|---|---|
| LENS-DOMAIN | 전문가 관점 | 도메인 전문가 | 실행 | 기본 관점 |
| LENS-SECURITY | 전문가 관점 | 보안 전문가 | 실행 | 기본 관점 |
| SH-01 | stakeholder | 역할 이름 | 실행 | 요청 문구 "…"가 이 카드의 목표 "…"와 닿는다 |
| SH-02 | 제약 출처 | 이름 | 제약 전달 | persona로 실행하지 않고 제약을 모든 persona에 전달했다 |
| SH-03 | stakeholder | 역할 이름 | 미선택 | 요청과 닿는 문구가 없다 / 상한 3을 넘어 제외했다 / 카드 형식 오류: 오류 메시지 |

## 4. 업무 주체 초안

| 행위자 | 권한 | 출처 | 상태 |
|---|---|---|---|
| 행위자 이름 | 할 수 있는 일과 할 수 없는 일 | 요청 해석(에이전트 제안): "요청 문구 인용" | draft |

사용자가 확인하면 `상태`를 `confirmed`로 바꾸고 `출처`에 확인한 `question_id`를 더한다. 사용자가 고친 부분은 사용자 문구로 쓴다.

## 5. 후보 요구사항

| CAND | 제안자 | 종류 | 내용 | 요청 앵커 | 근거 | 결정 | 결정 출처 |
|---|---|---|---|---|---|---|---|
| CAND-01 | LENS-DOMAIN, SH-01 | 업무 규칙 | persona가 낸 문장 | "요청 원문 인용" | persona의 근거 | 채택 | `<execution_id>:1` |
| CAND-02 | LENS-SECURITY | 예외 | … | "…" | … | 기각 | `<execution_id>:2` |
| CAND-03 | SH-01 | 목표 | … | "…" | … | 대기 | |

## 6. 충돌

| 충돌 | 요청 앵커 | 입장 | 라운드 2 결과 | 결정 | 결정 출처 |
|---|---|---|---|---|---|
| CONF-01 | "요청 원문 인용" | CAND-03 대 CAND-05 | CAND-03 제안자: keep. CAND-05 제안자: concede | CAND-03 채택, CAND-05 기각 | `<execution_id>:6` |

충돌이 없으면 `없음`으로 쓴다.

## 7. 요구사항 초안

상태는 모두 `draft`이며 `spec-me`가 사용자 확정 요구사항으로 이어받는다.

### 7.1 업무 목적

- 요청이 말한 범위를 그대로 옮긴 목적 문장 (요청 원문: "요청 원문 인용")
- 채택한 결정을 옮긴 목적 문장 (CAND-01)

### 7.2 업무 주체

- 행위자: 권한 (확정 `question_id`)

### 7.3 참여한 stakeholder

- ID 역할: 이 요구사항에 기여한 CAND (CAND-01, CAND-04). 실행한 stakeholder 카드와 전문가 관점만 쓴다.

### 7.4 정상 시나리오 초안

1. 행위자가 … 한다 (CAND-01)

### 7.5 예외 시나리오 초안

- 조건에서는 … 한다 (CAND-02)
````

## 생략 판정의 문서

`판정: 생략`이면 1절과 2절만 채우고 3~7절은 `해당 없음 — 생략 판정`으로 쓴다. 근거에는 확인한 기존 Spec 경로를 적는다.
