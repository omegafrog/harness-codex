# 기술 선택

중요한 기술 선택이 미완료이거나 기존 결정이 확정된 요구·제약을 충족하지 못할 때만 이 절차를 수행한다. 유효한 기존 결정은 재사용한다. Product 요구, System Targets, 기존 ADR·제약·승인된 프로젝트 지식과 명시적 사용자 답변·위임을 먼저 확인한다.

1. 요구 ID별 필수·선호 기준과 우선순위를 확정한다. 기능, 구축 시간, 운영 책임, 비용, 데이터 제어, 성능과 변경 가능성 중 적용되는 것만 선택한다. 수치는 목표·단위·조건·출처를, 정성 기준은 판정 조건을 기록한다. 미확정 값을 만들지 않는다.
2. 같은 기능과 운영 책임을 제공하는 후보 조합을 구성한다. 기존 구성이 유효하면 후보로 포함한다. 실제 대안이 없으면 단일 후보와 이유를 기록한다.
3. 부족한 사실만 조사한다. 관련 ADR·공식 문서·기존 실측을 우선하고 각 주장에 출처 위치, 버전·조건, 확인일을 기록한다. 실측, 외부 측정, 문서 사실, 추정, 미확인을 구분한다. 비교할 수 없는 조건의 성능 수치를 직접 비교하거나 외부 측정을 현재 앱의 실측으로 표시하지 않는다.
4. 모든 후보를 같은 기준으로 충족·미충족·미확인과 이유를 비교한다. 직접 운영할 작업, 추가 구현 범위와 비용 조건을 구체적으로 설명한다. 사용자에게 필수 조건 충족 여부, 기준별 차이, 감수할 단점과 추천을 함께 제시하고 실제 선택 또는 명시적 위임을 기록한다. 이미 위임된 선택은 반복 승인 없이 이유를 남긴다. 독립 질문은 한 묶음으로 `spec-me`에 반환한다.
5. 기존 Architecture Decision에 기준·평가·출처·선택·수용한 단점·불확실성·재검토 조건을 기록하고 Architecture Spec의 Alternatives and Trade-offs에 결과를 반영하도록 반환한다. 형식은 `.codex/schemas/decision/architecture-decision.schema.yaml`과 runtime validator를 따른다. `review_mode`는 기본 `Normal`이며 사용자가 Learning을 요청하면 `Learning`과 해당 `review_id`를 기록한다. 사용자 선택 또는 위임은 자료 열람 동의와 구분한다.

일반적인 비교 출처는 인용만으로 사용한다. 원문 snapshot·별도 자료 사용 승인·Evidence 등록을 요구하지 않는다. 기존 승인된 Principle/Evidence는 재사용할 수 있으며, 새 자료를 공통 Knowledge로 게시할 때만 `knowledge-harvest`의 검토·승인·게시 절차를 따른다. 이 GUIDE는 Product/Architecture Spec 작성, 독립 Spec 리뷰와 티켓 발행을 소유하지 않는다.
