# Review routing

`to-ticket` owns its independent plan-review loop. It calls a fresh, read-only `plan_reviewer` native subagent, records each review, revises when needed, and returns completed only after the canonical planning review is current and passing. Tracker publication is a separate `tracker-publish` workflow stage.

After canonical plan writing, the `to-ticket` execution creates an attempt with `harness-plan-review.mjs begin`, passes the exact admission snapshot to a fresh reviewer, validates the result against `plan-review/review-record.schema.json`, saves the review record in its session, and records it with the same attempt ID. The reviewer must assess the admitted planning workspace and exact Product/Architecture Specs, index, and plans. It must not require the implementation target to be that workspace or prescribe an implementation target; use the declared return root when no explicit target was requested. A `revise` verdict causes the same author execution to repair the plans and start a new attempt with a different reviewer. A `pass` verdict completes the stage only after `check --phase planning` confirms the canonical review is current. Before dispatching `tracker-publish`, the orchestrator presents the full reviewed plan set and obtains the user's final publication approval.

The reviewer input is the whole snapshot on the first attempt. Re-review uses `review_delta`, prior findings, and directly affected relationships; ambiguous scope requires reading the full affected document. The reviewer returns all snapshot `{path, sha256}` pairs. The record CLI converts this array into the path-to-hash map used by the review ledger and rejects a stale snapshot.

Record actual author execution IDs and reviewer IDs, keep `fork_turns: none`, and never treat a user answer as a review pass. After three substantive attempts without a pass, ask the user to resolve the concrete scope or decision. The completion runner and publisher stage both verify the latest review against current files; tracker and Beads changes happen only in the publisher stage after the precheck passes.
