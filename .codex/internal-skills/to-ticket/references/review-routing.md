# Review routing

`to-ticket` owns its independent plan-review loop. It calls a fresh, read-only `plan_reviewer` native subagent, records each review, revises when needed, and returns completed only after the canonical planning review is current and passing. Tracker publication is a separate `tracker-publish` workflow stage.

After canonical plan writing, the `to-ticket` execution creates an attempt with `harness-plan-review.mjs begin`, passes the returned `reviewer_input_ref` to a fresh reviewer started with an empty context, and records the attempt with `harness-plan-review.mjs record --attempt <id>`. The subagent hook supplies the verdict, findings and reviewer identity; the stage never writes them. The referenced runner-owned JSON contains the exact admitted file contents and hashes; use it as the complete current snapshot and never discover review inputs by searching `.io` or reading archived restart documents. The reviewer must assess the admitted planning workspace and exact admitted design documents (requirements, tactical design, glossary and map, technology/UI/API/data decisions), index, and tickets. It must not require the implementation target to be that workspace or prescribe an implementation target; use the declared return root when no explicit target was requested. A `revise` verdict causes the same author execution to repair the plans and start a new attempt with a different reviewer. A `pass` verdict completes the stage only after `check --phase planning` confirms the canonical review is current. Before dispatching `tracker-publish`, the orchestrator presents the full reviewed plan set and obtains the user's own publication reply, which it passes to the runner verbatim.

The reviewer input is the whole snapshot on the first attempt. Re-review uses `review_delta`, prior findings, and directly affected relationships; ambiguous scope requires reading the full affected document. The reviewer returns only its verdict and findings. The runner binds the exact admission file and input hashes to the attempt; `record` compares that admission with the active ledger and evaluates the current workspace snapshot, recording stale results as stale.

Record actual author execution IDs and reviewer IDs, keep `fork_turns: none`, and never treat a user answer as a review pass. After three substantive attempts without a pass, ask the user to resolve the concrete scope or decision. The completion runner and publisher stage both verify the latest review against current files; tracker and Beads changes happen only in the publisher stage after the precheck passes.

**Handoff to the caller.** A Claude Code stage subagent has no `Agent` tool and cannot start the reviewer; a Codex stage may use the same handoff instead of running the loop itself. After the canonical plans and index are written and `check --phase planning` has no preparation errors, return `action_required/REVIEW_REQUIRED` with a `review_request` for `plan_reviewer` instead of `blocked/ENVIRONMENT_UNAVAILABLE`. The caller (main session) then runs `harness-plan-review.mjs begin`, starts a fresh `plan_reviewer` with the returned `reviewer_input_ref`, runs `record --attempt <id>`, and passes the recorded result back to this stage with `--feedback`. Do not write the verdict or reviewer identity yourself.
