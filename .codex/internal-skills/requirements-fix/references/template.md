# requirements.md 템플릿

`docs/specs/<plan-set-id>/requirements.md`는 새 기능 요청의 요구사항을 한 문서에 모아 가는 living spec이다. 여러 stage가 이어서 채우고 마지막 `bounded-context`가 확정한다. 이 문서가 최종 모양의 정본이며 다른 stage는 이 템플릿을 링크한다. 사람이 읽는 문서이므로 한국어로 쓰고 ID, JSON 키, 경로, CLI 명령은 원형을 유지한다. 해당 사항이 없는 절에는 `해당 없음 — 이유`를 적는다.

## 단계별 기입

| stage | 이 문서에서 하는 일 |
|---|---|
| `stakeholder-analysis` | 문서를 만들고 헤더와 `### 요구사항 초안`을 쓴다. 후보 표와 충돌 기록은 `stakeholder-analysis.md`에 둔다 |
| `subdomain-candidates` | `## 1` 서브도메인 표를 쓰고(`분류`는 `미정`) `### 요구사항 초안`을 `### BIZ-xx` 절로 나눠 옮긴 뒤 지운다 |
| `ubiquitous-language` | 후보 업무의 혼동되는 용어를 먼저 정하고 `## 3`과 `CONTEXT.md`에 범위·근거를 기록한다. 실제 BC 소속은 나중에 검증한다 |
| `event-storming` | BIZ별 이벤트 흐름 표, `## 4`, `## 5`, hotspot 답에서 나온 업무 규칙·예외, 다이어그램 링크를 쓴다 |
| `subdomain-classification` | 이벤트 근거로 서브도메인 경계를 검증하고, 사용자 확인을 받아 SD 표의 `분류`·`근거`·`상태`를 `confirmed`로 쓴다. 경계가 바뀌면 BIZ 배치와 이벤트 다이어그램도 고친다 |
| `requirements-fix` | 남은 빈칸을 인터뷰로 채우고 완료 조건과 `## 6`을 쓴 뒤 coverage gate(바운디드 컨텍스트 행 제외)를 통과시킨다. `상태`는 `draft`로 둔다 |
| `bounded-context` | 빈칸이 채워진 요구사항을 근거로 `### 1.1` 바운디드 컨텍스트 표를 쓴다. 같은 stage가 `CONTEXT-MAP.md`와 용어의 최종 BC 소속을 갱신하고, coverage gate 전체를 통과하면 `상태`를 `fixed`로 바꾼다 |
| `domain-model`부터 `context-boundary`까지 | 이 문서를 확정 입력으로 읽고 [tactical-design.md 템플릿](../../domain-model/references/template.md)의 문서를 채운다. 업무 조건·예외·결과가 빠졌으면 해당 BIZ와 근거를 `requirements-fix`에 반환한다 |

`stakeholder-analysis`가 `판정: 생략`이면 이 문서를 만들지 않는다. 뒤의 여섯 stage와 전술 설계 stage는 문서를 쓰지 않고 생략을 결과 요약에 기록한 뒤 `completed/OK`를 반환하며, 이후 필요한 구현 흐름은 별도로 판단한다.

## 작성 규칙

- ID는 `SD-01`(서브도메인 후보), `BIZ-01`(업무), `INV-01`(업무 규칙), `EX-01`(예외 시나리오), `AC-01`(완료 조건), `HS-01`(hotspot)이다. INV·EX·AC·HS는 BIZ와 무관하게 문서 전체에서 번호가 유일하다. 한 번 붙인 ID는 바꾸지 않으며 지운 항목의 번호는 다시 쓰지 않는다.
- 모든 항목 끝에 출처를 붙인다: `요청 원문`, `CAND-xx 채택`, `answers.json`, `요청 해석(에이전트 제안)`. `answers.json` 출처에는 사용자 답변의 `question_id`를 함께 적는다. 에이전트 판단을 사용자 결정 출처로 쓰지 않는다.
- 항목 상태는 출처가 정한다. 에이전트 제안만 근거인 항목은 `draft`, 요청 원문·채택 후보·사용자 답변이 근거인 항목은 사용자 확정이다. 문서가 `fixed`가 되면 모두 확정으로 본다.
- 문서 상태는 `draft`와 `fixed`뿐이고 BIZ의 `상태`도 같다. SD의 `상태`는 후보인 `draft`, 사용자가 경계와 분류를 확인한 `confirmed`, 문서 확정 때 `fixed`다. `confirmed`는 `subdomain-classification`만, `fixed`는 `bounded-context`만 쓴다.
- 업무 단위(BIZ)는 행위자가 한 번에 끝내는 업무 하나다. 정상 시나리오는 그 업무의 시작부터 끝까지이고, 규칙·예외·완료 조건은 그 업무에 속한다.
- `6.1`은 stakeholder-analysis가 정한 행동 범위의 정본이다. `subdomain-candidates`만 포함 행동을 BIZ에 배정하고 BIZ에서 ACT와 근거로 되돌아가는 연결을 채운다. 각 필드에는 한 소유자만 둔다.
- 시나리오에는 BIZ 안에서 안정적인 `SC-xx`를 붙여 정상, 유효 대안, 거절/실패 결과를 구분하고 INV/EX와 AC에 연결한다. 적용하지 않는 경로는 `NOT_APPLICABLE — 구체적 이유`로 적는다.
- AC는 `조건 / 행위 / 관찰 가능한 업무 결과 / 변경 또는 보존 상태`를 담고 관련 SC·INV·EX를 연결한다. `오류 발생`만으로 완료 조건이 되지 않는다. 기술 응답 코드, API, DB, aggregate나 Gherkin runtime은 적지 않는다.
- 기각·보류한 후보와 `요청 범위 밖 관찰`은 이 문서에 쓰지 않는다. 사용자의 새 결정이 있어야 들어온다.
- 바운디드 컨텍스트의 비교 기준은 [ddd-design](../../ddd-design/GUIDE.md)의 경계 규칙이 정본이며 이 문서에 다시 적지 않는다.
- 업무와 전략적 경계만 다룬다. bounded context는 `bounded-context` stage만 정하며, 모듈·저장 방식·프레임워크·통신 방식은 쓰지 않는다.
- BIZ의 각 필드(`업무 규칙`, `예외 시나리오`, `이벤트 흐름` 등)는 BIZ마다 한 번만 둔다. 필드를 채울 때는 그 필드의 기존 줄(`없음 — 후속 stage가 채운다` 포함)을 그 자리에서 바꾸며, 같은 이름의 필드를 BIZ 끝에 새로 덧붙이지 않는다. 고치기 전에 해당 BIZ 절을 다시 읽고, 패치 hunk는 `@@ ### BIZ-xx <업무명>`처럼 BIZ 제목을 문맥으로 둔다. 빈칸 줄과 표 머리줄은 BIZ마다 같아서 제목 없는 hunk는 다른 BIZ에 맞거나 실패한다. 실행기는 요구사항 stage가 질문을 반환하거나 완료할 때 한 BIZ에 같은 필드가 두 번 있으면 거부한다.
- 확정 뒤 변경은 사용자의 명시적 수정 지시로만 한다. 그 지시는 출처 `사용자 수정 지시`로 `출처·변경 이력`에 원문과 함께 남긴다.
- 전술 설계에서 기존 승인 범위를 바꾸는 결정이 나오면 `requirements-fix`가 수정 근거를 검토한다. 요구 변경은 `bounded-context`의 확정과 사용자 승인을 받은 뒤 설계에 반영한다.

## 문서 모양

````markdown
# 요구사항 명세

- plan set: `<plan-set-id>`
- 상태: draft | fixed
- 요청 원문:

  > 사용자의 요청을 수정·요약 없이 그대로 옮긴다.

- 참여한 stakeholder: LENS-DOMAIN 도메인 전문가 (CAND-01, CAND-03), SH-01 모더레이터 (CAND-02)

## 1. 서브도메인 후보

서브도메인 후보는 `subdomain-classification`에서 사용자가 확인하기 전까지 가설이다. 업무 묶음과 분류만 정하며 모듈·기술은 정하지 않는다.

| SD | 이름 | 업무 범위 | 포함 업무 | 핵심 용어 후보 | 분리 이유(가설) | 분류 | 근거 | 상태 |
|---|---|---|---|---|---|---|---|---|
| SD-01 | 게시판 | 회원이 글을 쓰고 지우는 업무 | BIZ-01, BIZ-02 | 게시글, 댓글 | 기존 영역 확장: CONTEXT-MAP의 "커뮤니티" | core | 이 요청이 만드는 차별점이다 — 출처: answers.json `<question_id>` | confirmed |
| SD-02 | 신고 처리 | 신고를 받아 처리하는 업무 | BIZ-03 | 신고, 조치 | 새 후보: 행위자와 쓰는 말이 게시판과 다르다 | 미정 | - | draft |

`분리 이유(가설)`은 기존 영역에 넣었으면 `기존 영역 확장: <이름>`, 새로 나눴으면 `새 후보: <업무 목적·언어·행위자 차이>`로 시작한다. `분류`는 `core`(이 요청에서 차별되는 것), `supporting`(필요하지만 차별되지 않는 것), `generic`(인증처럼 흔한 것) 중 하나이고 확인 전에는 `미정`이다. `근거`는 `requirements.md`의 업무·이벤트에서 끌어온 이유와 출처다. 합치거나 나눠 없어진 SD의 번호는 다시 쓰지 않는다.

### 1.1 바운디드 컨텍스트

`bounded-context` stage가 쓴다. 컨텍스트는 서브도메인 하나나 기능 이름에서 곧바로 나오지 않는다.

| BC | 포함 SD·BIZ | 책임 | 소유 규칙·데이터 | 근거 | 비교한 대안 |
|---|---|---|---|---|---|
| community (커뮤니티) | SD-01(BIZ-01, BIZ-02), SD-02(BIZ-03) | 글과 그에 대한 신고 처리를 한 언어로 다룬다 | INV-01, INV-02: 게시글과 신고 | 기존 컨텍스트 확장: CONTEXT-MAP의 "커뮤니티". 신고 용어가 게시글과 같은 뜻이다 — 출처: answers.json `<question_id>` | 신고를 별도 컨텍스트로 분리: 용어와 규칙 소유가 같아 합치는 쪽이 낫다 |

`BC`의 소문자 slug는 `CONTEXT-MAP.md`의 Context ID와 일치해야 한다. `근거`는 기존 컨텍스트에 먼저 넣었는지, 어떤 경계 기준이 결과를 갈랐는지와 출처를 적는다. `비교한 대안`에는 합친 안과 나눈 안을 공정하게 적는다.

## 2. 업무

### 요구사항 초안

`stakeholder-analysis` 직후부터 `subdomain-candidates` 전까지만 있는 임시 절이다. 아래 다섯 줄을 쓰고, `subdomain-candidates`가 BIZ 절로 옮기면서 이 절을 지운다.

- 업무 목적: 요청이 말한 범위 (요청 원문: "요청 원문 인용")
- 업무 주체: 행위자: 권한 — 출처: answers.json `<question_id>`
- 참여한 stakeholder: LENS-DOMAIN: CAND-01
- 정상 시나리오 초안: 1. 행위자가 … 한다 — 출처: CAND-01 채택
- 예외 시나리오 초안: 조건에서는 … 한다 — 출처: CAND-02 채택

### BIZ-01 게시글 작성 (SD-01)

- 상태: draft | fixed
- 업무 목적: 회원이 자기 글을 게시판에 올린다 — 출처: 요청 원문 "…"
- 업무 주체: 회원: 작성할 수 있다 — 출처: answers.json `<question_id>`
- 행동 ID: ACT-01 — 근거: 요청 원문 "커뮤니티 기능"
- 참여한 stakeholder: LENS-DOMAIN: CAND-01
- 정상 시나리오:
  - SC-01 정상: 회원이 제목과 본문을 입력해 게시하고 게시글이 목록에 나타난다 — 출처: CAND-01 채택; AC: AC-01
  - SC-02 유효 대안: 회원이 임시 저장한 글을 이어 작성해 게시한다 — 출처: answers.json `<question_id>`; AC: AC-01

  - INV-01 [SC-01, SC-02] 본문은 5,000자 이하여야 한다 — 출처: answers.json `<question_id>`
- 예외 시나리오:

  - AC-03 [SC-03, EX-01] 조건: 비회원이 글 게시를 시도한다; 행위: 게시를 요청한다; 관찰 결과: 권한 거절이 안내되고 게시글이 생성되지 않는다; 상태: 게시글 없음 — 출처: answers.json `<question_id>`

  - event-storming: 이벤트 흐름과 HS-01 결정을 INV-01로 반영

## 3. 용어

같은 단어를 같은 뜻으로만 쓰기 위한 표다. 여러 표현이 섞이거나 헷갈리는 말만 올린다. 사용자 답으로 정한 줄은 `뜻` 끝에 `(answers.json)`을 붙인다. 초기에는 기존 컨텍스트 또는 후보 BIZ 범위로 기록하고, 확정되지 않은 소속은 `범위 미확정`으로 표시한다. `bounded-context`가 나중에 실제 소속을 검증한다. 컨텍스트마다 뜻이 다른 말은 각 범위에 한 줄씩 쓰고 `용어` 칸에 범위를 붙인다. 한 뜻으로 쓰는 말은 한 줄이다.

| 용어 | 뜻 | 쓰지 않을 말 |
|---|---|---|
| 게시글 | 회원이 게시판에 올린 글 하나 (answers.json) | 포스트, 글 |
| 회원 (커뮤니티) | 글을 올릴 수 있는 로그인한 사용자 | 유저 |
| 회원 (결제) | 결제 수단을 등록한 사용자 | 고객 |

## 6. 공통

### 6.1 범위·비목표

- 포함: 아래 행동 범위 표의 포함 행동과 요청된 기능 — 출처: ACT 표 및 요청 원문
````
