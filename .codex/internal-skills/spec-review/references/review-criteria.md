# Architecture Spec 독립 리뷰 기준

리뷰 자료는 Product Spec과 Architecture Spec 두 문서다. Product Spec은 요구사항 기준이고 Architecture Spec이 리뷰 대상이다. 다른 파일이나 외부 자료를 읽지 않는다.

다음의 구체적인 결함만 확인한다.

- Product의 핵심 요구사항과 수용 조건이 Architecture에 빠졌거나 두 Spec이 모순되는지.
- Domain의 Entity와 Value Object, 필수 Aggregate와 root, application service, BC의 역할과 관계가 명확하고 업무 규칙의 책임이 일관되는지.
- 핵심 동작과 데이터, 저장·조회 등 요구사항 구현에 필요한 설계가 빠졌는지.
- 변경되는 핵심 업무 규칙의 테스트 사례가 조건과 기대 업무 결과를 설명하는지.
- 수치·길이·경계·형식·검증 규칙과 삭제 전파 규칙에 Product Spec의 `의도`와 `충분한 수준`이 있는지(재리뷰에서는 새로 추가·변경된 규칙을 반드시 포함), Architecture가 그 수준을 넘겨 규칙을 강화하지 않았는지. Architecture의 제약이 Product의 의도·규칙 ID를 인용하는지 확인한다. 근거 ID가 없는 제약과, 의도 없이 정규화·인코딩·locale 같은 높은 정밀도를 요구하는 규칙은 근거 없는 엄밀함으로 지적한다.

- Product Spec 13절 사용자 시나리오의 모든 단계가 기존 UC/BR/AC에서 나오는지, 시나리오를 위해 추가된 요구에 사용자 답변 출처가 있는지(출처 없이 추가됐으면 지적한다), 시나리오가 핵심 Use Case를 끝까지 따라가고 단계마다 요구 ID가 있는지, Architecture Spec 12.7 실행 환경이 그 시나리오를 실행할 수 있는지. 의도의 충분한 수준을 넘는 시나리오·환경(부하·장애 주입·별도 인프라)은 과한 설계로 지적한다.
- 과한 설계: Product의 INT·BR·AC나 필수 DDD 구성(Entity·Value Object·Aggregate root, application service, repository, transaction)에 근거하지 않은 결정·규칙·구성요소·검증 요구가 있는지. 예: 요청되지 않은 보안 강화(세션 자동 만료, 동시 접속 제한, 계정 잠금), 의도에 비해 과한 동시성·장애 복구·운영 설계, 한 구현뿐인 불필요한 port, pass-through service. 의도의 `충분한 수준`을 넘는 것은 제거를 요구하는 major로 지적하고, 근거 INT·BR이 있으면 그 수준에 맞게 줄이라고 쓴다. 플랫폼 기본 동작을 그대로 쓰는 것은 과한 설계가 아니다.
- INT의 `충분한 수준`이 관찰 가능한 사용자 흐름·완료 조건을 제시하는지, 파생 설계마다 없을 때 실패하는 UC/BR/AC·공통 기본선을 설명하는지 확인한다. 넓은 의도나 DDD 명칭만으로 필요성이 입증되지는 않는다. 누락 지적에도 같은 필요성 기준을 적용하고 선택적 개선을 필수 수정이나 질문으로 만들지 않는다. 규칙은 기존 INT를 참조할 수 있고, 별도의 목적 답변이 없다는 것만으로 차단하지 않는다. 요청 해석은 에이전트 제안과 근거로 표시했는지 확인하고 사용자 승인으로 취급하거나 새 요구를 끼워 넣지 않았는지 검토한다. 보안·권한·데이터 보호와 일반 오류 처리는 유지한다.

스펙에 적힌 설계만 판단한다. 공식 문서나 기술 근거를 검증하거나, 다른 파일의 용어 동기화, 기술 대안 비교의 충실도, 모든 운영 지표를 독립 심사하지 않는다. 스펙 외 자료가 필요할 정도로 설계가 빠진 경우에는 그 누락과 영향을 스펙 위치에 연결한다. 취향, 문서 서식, 가상의 미래 위험은 finding이 아니다.

중대한 요구사항·설계 누락이나 모순은 blocker/major로 묶어 한 번에 반환한다. 사소한 개선은 minor이며 통과를 막지 않는다. 재리뷰는 수정 부분, 미해결 지적 및 직접 영향받는 관계만 확인하고 무관한 기존 통과 부분을 유지한다.
