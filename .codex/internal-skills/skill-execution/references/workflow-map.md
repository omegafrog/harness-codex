# Workflow 지도

요청과 기존 답변·위임을 확인하고 필요한 setup과 worktree를 준비한다. 새 기능의 요구사항 흐름은 `stakeholder-analysis`가 요청 범위의 후보 요구사항을 독립 persona에게서 모아 사용자가 하나씩 채택하게 하고(자명한 변경은 이 흐름 전체를 건너뜀), `subdomain-candidates`가 서브도메인 후보와 업무(BIZ)로 나누고, `ubiquitous-language`가 후보 업무별 용어를 먼저 정하고, `event-storming`이 업무별 이벤트 흐름·hotspot 답·PlantUML 다이어그램을 쓰고, `subdomain-classification`이 이벤트 근거로 경계를 검증해 core·supporting·generic 분류와 함께 사용자 확인을 받고, `bounded-context`가 바운디드 컨텍스트를 정해 `CONTEXT-MAP.md`에 반영하고 용어의 최종 컨텍스트 소속을 검증하며, `requirements-fix`가 남은 빈칸을 한 번의 인터뷰로 채워 `requirements.md`를 `fixed`로 확정한다. 이어서 전술 설계 흐름이 `domain-model`(바운디드 컨텍스트별 Entity·Value Object 후보와 업무·규칙·이벤트 매핑, 기존 프로젝트면 `code-research`), `aggregate-design`(불변식으로 Aggregate를 묶거나 상태 없는 컨텍스트는 이유와 함께 Aggregate 없이 두고, Aggregate에 걸친 규칙의 일관성을 정하며 근거가 없으면 사용자에게 묻는다), `domain-service`(어떤 모델도 소유하지 못하는 도메인 판단만), `application-service`(호출 순서·transaction 경계·Repository·외부 효과), `integration-design`(컨텍스트 사이의 명령·응답·이벤트와 통신 방식, 업무 결과가 갈리면 사용자에게 묻는다), `context-boundary`(관계 패턴·코드 의존 형태·경계 강제 방식) 순서로 `docs/specs/<plan-set-id>/tactical-design.md`를 채운다. 앞 다섯 stage는 gate 없이 완료하고, 마지막 `context-boundary`가 `completed/OK`를 반환할 때 실행기가 결정론적 gate `harness-domain-model-check.mjs`로 `tactical-design.md` 전체를 한 번 검사해 실패하면 `gate_error`로 되돌리며 발견 사항의 `owner_stage`가 다시 열 앞 stage를 가리킨다. Gate 통과 뒤에는 별도 `tactical-to-code` workflow가 `tactical-technology` → `tactical-ui` → `tactical-api` → `tactical-data` → `to-ticket` → `tracker-publish` → `tactical-code`로 기존 전술 설계를 구현한다. 새 기능 흐름은 Product·Architecture Spec을 거치지 않는다.

`to-ticket`은 전술 설계(`requirements.md`·`tactical-design.md`·`CONTEXT*.md`)와 technology·UI·API·data 결정 문서를 바운디드 컨텍스트·업무(BIZ) 단위의 vertical ticket으로 나눈다. 상류 컨텍스트가 공개하는 API·이벤트 ticket이 그것을 쓰는 하류 ticket보다 먼저 오도록 의존 순서를 정하고, 각 ticket은 소유 INV/EX/AC와 검증 테스트, 접하는 컨텍스트와 6절 경계 규칙(데이터 소유·허용 의존·경계 강제 검사), 의존한 결정과 완료 기준을 담는다. 같은 stage 안에서 fresh `plan_reviewer`가 설계 문서·index·전체 ticket을 대조해 통과할 때까지 반복한다. 그 뒤 orchestrator가 ticket 계획 전체를 사용자에게 보여주고 사용자가 직접 답해야만(`--approval-answer`가 사용자 입력 기록과 맞아야 한다) `tracker-publish`가 계획을 GitHub Project에 발행하고 저장소 Issue·sub-issue 관계까지 활성화한다. 요청이 계획까지면 여기서 멈추고 `to-ticket` 완료 gate를 실행한다. 구현 요청이 있으면 `tactical-code`가 ready ticket을 하나씩(의존 순서) 구현하고 ticket마다 commit 하나와 그 ticket의 테스트를 남기며, 모든 ticket이 완료되면 `tactical-to-code` 완료 gate가 열린다. 사용자 경로 E2E는 사용자가 요청할 때 별도 `e2e-test`가 실행하며 실패 시 자동 수정·재실행 없이 사용자에게 확인한다. Spec 기반 legacy 계획은 `implement-wrapper`가 계획별 구현과 독립 코드 리뷰를 수행하고 `sync-contracts`가 통합 계약을 seal한다.

정본은 `worktree.json`, 프로젝트 Spec·계획, session의 stage result·review history와 configured tracker의 발행 상태이다. runner는 실행 식별자와 현재성 기록을 관리하고 작성자는 제품 산출물을 작성한다. 추가 ledger를 만들지 않는다. stage 결과·미해결 findings와 gate, 사용자 질문별 답변·승인·위임, provider/session과 실제 process 상태를 확인해 다음 단계를 고른다. 요약이 부족하면 해당 정본을 읽는다. 완료된 조사는 재실행하지 않고 독립 질문은 묶으며 수정 요청은 소유 단계로 반환한다.

필수 독립 리뷰, 실제 승인, 실행 전제와 중복 process 방지는 생략하지 않는다. 같은 provider는 session을 재개하고 다른 provider는 이전 입력과 결과를 읽는 새 session을 사용한다. 진행 중 process의 생존 여부를 확인한다. 실패·취소 시 기록을 보존하며 worktree 삭제나 상태 수작업 변경으로 복구하지 않는다. 각 실행 절차는 [실행 조율](../GUIDE.md), 리뷰와 발행의 해당 GUIDE가 소유한다.

# 전술 설계에서 구현까지

전술 설계가 모두 `completed/OK`인 뒤 별도 `tactical-to-code` workflow를 시작한다. stage 순서는 `tactical-technology` → `tactical-ui` → `tactical-api` → `tactical-data` → `to-ticket` → `tracker-publish` → `tactical-code`이며 runner가 이전 결과와 전술 설계 완료를 확인한다. 이 흐름은 전술 설계 문서를 소비하고 ticket을 거쳐 application code와 test를 만든다. 요구사항 재시작 흐름에 넣지 않으므로 그 재시작은 application code를 복원하거나 삭제하지 않는다.

기술 stage는 기존 stack을 먼저 평가하고, 필요한 기술 결정을 기존 `technology-selection`의 비교 기준과 공신력 있는 근거로 정리한다. `tactical-ui`는 적용 여부를 판단한다. 화면 설계가 필요해 `blocked/DEPENDENCY_INCOMPLETE`를 반환하면 별도 `frontend-design` workflow의 `frontend-design-brief` stage를 실행하고, 그 결과로 `tactical-ui`를 feedback 재개한다. 완료된 design artifact는 ticket 분할과 리뷰의 근거다. ticket 발행 뒤 `frontend: true` ticket이 준비되면 독립 workflow의 `frontend-implementation --plan <ticket-id>`과 `frontend-visual-review --plan <ticket-id>`를 차례로 실행한 다음 `tactical-code --plan <ticket-id>`로 완료한다. visual review가 차단되면 같은 ticket의 frontend implementation을 수정하고 재검토한다. 이 독립 workflow를 implement의 하위 단계로 실행하지 않는다. `tactical-api`는 application entry와 API, `tactical-data`는 상태 저장·data ownership·storage 계약을 각각 결정한다.

`to-ticket`과 `tracker-publish`는 기존 계획 stage를 그대로 쓰되 입력이 Spec이 아니라 위 전술 설계와 결정 문서다. 발행은 사용자의 직접 답이 있어야만 진행한다.

`tactical-code`는 게시된 ticket 하나를 완료된 전술 설계·기술 결정과 ticket 파일에 근거해 구현·테스트하고 정확한 `commit_request`를 반환한다(ticket마다 한 번 실행, `--plan <ticket-id>`). 누락된 업무 결정은 추론하지 않고 차단한다. Workflow artifact는 프로젝트 소유이므로 Git에 보이며 설치된 Harness 자산은 Git에서 제외된다.
