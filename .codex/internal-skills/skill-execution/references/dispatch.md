# 서브에이전트 실행과 결과

stage는 현재 worktree에서 `node .codex/scripts/harness-native-stage.mjs launch --stage-id <stage> [준비 옵션]` 한 번으로 시작한다. 준비 옵션은 `harness-prepare-input.mjs`와 같다(`--answer`·`--feedback`·`--user-revision`·`--plan` 등). `--plan <ticket-id>`는 `tactical-code`가 ticket 하나를 구현할 때 쓰고(`harness-context.mjs`의 `ready_tickets`에서 고른다), `tracker-publish`는 `--publication-approved true --approval-answer '<사용자 답 원문>'`을 함께 받는다. `launch`는 입력을 준비한 뒤 `start`와 같이 출력 schema를 만들고 실행을 원자적으로 예약한다. 중복 예약이나 이미 실행 중인 stage는 중단한다. 반환된 `agent_profile`, `binding`, `guide`, `input_path`, `schema_path`, `output_path`와 `next.bind`·`next.finish`를 사용한다. 새 실행이 없는 경우(일부 답만 도착했거나 실행 중인 stage에 답을 저장한 경우)에는 준비기의 `waiting_for_*` 결과만 반환한다. 입력 준비와 예약을 따로 하는 `harness-prepare-input.mjs`와 `harness-native-stage.mjs start --execution-id <execution_id>`도 같은 계약으로 유지된다. 이 명령들은 현재 worktree에서 `--root`와 `--worktree-ref`를 스스로 찾으므로 붙이지 않는다.

출력은 기본이 compact다. `prepare`는 `execution_id`·`stage_id`·`next`만, `finish`는 `status`·`code`·`result_ref`·`next`와 요약·artifact(`kind`·`path`)·질문·리뷰 요청·`commit_sha`만 담고, `harness-context.mjs`는 끝난 stage를 한 줄로 줄인다. 전체 입력·해시·`result` 원문은 `--verbose`로만 출력하며 진단이 아니면 쓰지 않는다. 오류는 모두 `error`(무슨 일), `code`, `why`(이유)와 실행할 `next` 명령 또는 사용자에게 받을 `user_decision`을 가진 JSON 하나다. `next`를 그대로 따르고 원인을 찾으려고 Harness 소스나 state 파일을 읽지 않는다. 오류 `code`는 `STAGE_ORDER`·`NOT_RUNNING`·`PREVIOUS_RESULT_MISSING`·`PREVIOUS_UNRESOLVED`·`REVISION_TARGET`·`REVISION_REPEATED`·`USER_REVISION_REFUSED`·`RESTART_REFUSED`·`DISCARD_REFUSED`·`FEEDBACK_REFUSED`·`ANSWER_REFUSED`·`STAGE_RUNNING`·`NOT_BOUND`·`INPUT_NOT_FOUND`·`WRONG_WORKSPACE`·`FORMAT_ERROR`·`GATE_ERROR`·`RESULT_REJECTED`·`COMMIT_BLOCKED` 등이며 알 수 없는 오류도 `next`나 `user_decision`을 가진다.

오케스트레이터(메인 세션)는 이 값을 서브에이전트에 전달만 한다. `guide`·`input_path`·`schema_path`의 파일과 stage 산출물(Spec·plan·코드) 본문은 읽지 않는다. 그 파일은 서브에이전트의 컨텍스트에서 읽는 것이고, 메인이 읽으면 이후 모든 턴에 남는다. 메인은 `finish`가 출력하는 `status`·`code`·`result_ref`와 `result`의 요약·artifact 참조·질문만으로 다음 단계를 정한다. 리뷰어에게는 문서 경로만 넘기고 리뷰어가 직접 읽게 한다.

현재 CLI의 native 서브에이전트 도구를 호출한다. Codex는 `spawn_agent`에 `fork_turns: "none"`을 명시하고, Claude Code는 상위 대화 이력을 전달하지 않는 fresh `Agent`를 사용한다. 새 stage에는 상위 대화·도구 출력·문서 본문을 복사하지 않고 아래 파일 경로와 실행에 필요한 값만 전달한다. 실제 결정과 답변은 입력에 참조된 파일에서 읽는다. 호출이 완료 전에 실제 agent ID를 반환하고 해당 agent에 메시지를 전달할 수 있어야 한다. Claude Code에서는 이를 지원하는 경우 백그라운드로 시작한다. 이 기능이 없으면 agent를 시작하기 전에 실패를 보고한다. 반환된 `agent_profile` role을 지정하고 그 profile의 sandbox 및 권한을 유지한다. profile을 선택할 수 없거나 지정된 권한을 적용할 수 없으면 실행하지 말고 실패를 보고한다. 반환된 `binding`의 model과 reasoning effort를 지원하는 도구에 그대로 지정한다. 독립 리뷰 등 fresh context가 필요한 role의 기존 규칙을 유지한다. 에이전트는 실제 agent ID를 전달받기 전 작업을 시작하지 않는다. 에이전트에 다음을 전달한다.

- 반환된 `guide`와 `input_path`, `.codex/internal-skills/skill-execution/worker-base.md`를 읽고 입력에 지정된 stage를 수행한다.
- `schema_path`의 JSON schema를 읽고 그 형식에 맞는 JSON을 `output_path`에 작성한다. 읽기 전용 profile이면 JSON 전체를 마지막 응답으로 반환한다. 실제 경로는 반환값을 그대로 사용한다.
- Harness CLI 명령은 `node .codex/scripts/harness-native-command.mjs --root <workspace_root> --execution-id <execution_id> --agent-id <agent_id> -- node .codex/scripts/<명령> ...`로 실행한다. 래퍼가 이 실행에 필요한 정확한 stage 환경을 전달한다.
- 입력에 참조된 이전 결과, 답변, feedback을 읽어 결정과 진행 상태를 보존한다. 필요 없는 질문이나 승인을 만들지 않는다.
- `deferred_user_answers_unverified`가 있으면 실제 사용자 응답으로 보존하되 기존에 실제 표시한 질문 ID와 대조하기 전에는 결정이나 승인으로 적용하지 않는다. 이미 처리된 답은 중복 처리하지 않는다.

도구가 반환한 실제 agent ID를 즉시 `node .codex/scripts/harness-native-stage.mjs bind --execution-id <execution_id> --agent-id <agent_id>`로 기록한다. ID를 추정하지 않는다. bind가 성공하면 그 실제 ID를 해당 에이전트에게 전달해 작업을 시작시킨다. 실제 서브에이전트의 종료를 native 도구로 기다린다. 읽기 전용 profile이면 해당 도구가 반환한 JSON 원문을 `harness-native-stage.mjs receive --execution-id <execution_id> --agent-id <agent_id>`의 표준 입력으로 전달한다. 응답을 수정하거나 재구성하지 않는다. 종료하지 않은 agent에 같은 작업을 중복 위임하지 않는다. 성공 또는 유효한 반환 결과가 나오면 같은 worktree에서 `node .codex/scripts/harness-native-stage.mjs finish --execution-id <execution_id>`를 실행한다. `format_error`이면 반환된 `errors`의 `path`, `rule`, `expected`, `value`를 **같은 서브에이전트에 전달**해 schema와 실제 파일을 다시 읽고 출력을 수정하게 한다. 수정 결과를 받은 뒤 같은 `finish`를 다시 실행한다. 오류를 숨기거나 임의로 출력 파일을 고치지 않는다. 전술 설계 흐름의 마지막 stage `context-boundary`가 `completed/OK`를 반환했지만 `tactical-design.md` 전체에 대한 gate `harness-domain-model-check.mjs`를 통과하지 못하면 `finish`는 아무것도 commit·기록하지 않고 `gate_error`(`gate`, `stage`, `errors`의 `code`·`message`·`id`·`owner_stage`, `instruction`)를 반환하며 stage는 `running`으로 남는다. 앞 네 stage(`domain-model`, `aggregate-design`, `domain-service`, `application-service`)는 gate 없이 받아들이므로 오류가 여기서 처음 드러난다. `errors`는 가장 앞 `owner_stage`부터 정렬되며 `owner_stage`는 잘못된 절을 채운 stage다. `errors`를 **같은 서브에이전트에 그대로 전달**한다. `owner_stage`가 `integration-design`이면 서브에이전트가 자기 절과 결정 이력을 고치고(gate만 통과시키려고 `requirements.md`나 앞 절을 고치지 않는다) 같은 `finish`를 다시 실행한다. `owner_stage`가 앞 stage이면 그 절은 확정된 입력이므로 서브에이전트가 `blocked` / `DEPENDENCY_INCOMPLETE`로 가장 앞 `owner_stage`를 가리키고 오류를 근거로 적은 뒤 같은 `finish`를 실행한다. 서브에이전트는 `result.owner_stage`(가장 앞 `owner_stage`)와 `result.dependency_gap`(오류 근거)을 반드시 적는다. 이 block은 사용자에게 묻지 않고 아래 [상위 stage 되돌아가기](#상위-stage-되돌아가기)로 자동 처리한다. 문서를 직접 고치거나 `harness-execution-state.mjs`로 완료를 기록해 우회하지 않는다(같은 gate가 거부한다). 에이전트가 반복해서 같은 오류를 고치지 못하거나 중단·실패하면 오류를 보고하고 멈춘다.

서브에이전트 도구가 실패나 취소를 확인한 경우에만 `node .codex/scripts/harness-native-stage.mjs fail --execution-id <execution_id> --reason <실제 실패>`로 실패를 기록한다. 사용자가 중단을 명시하고 서브에이전트의 종료가 확인된 경우에는 같은 명령의 `cancel`을 사용한다. 도구 반환 없이 에이전트가 종료했다고 추정하지 않는다. 세션 중단으로 agent의 상태가 불명확하면 자동 재실행하지 않는다. 같은 대화에서는 기존 세션의 실제 상태를 확인하고, 다른 Codex 대화가 시작한 stage(`inspect`의 `session`이 `other`이거나 `harness-context`가 `next`로 안내)는 그 대화로 돌아가지 않고 아래 인계를 쓴다.

다른 Codex 대화가 시작한 `running` stage는 새 대화에서 `node .codex/scripts/harness-native-stage.mjs launch --stage-id <stage> --take-over true`를 단독으로 실행해 인계한다. 실행기는 이전 orchestrator transcript가 이 worktree의 것이고 어느 process도 열고 있지 않은지, stage의 agent transcript도 닫혀 있는지, agent가 `finish`로 기록할 output을 남기지 않았는지, project worktree가 깨끗한지를 확인한다. 모두 확인되면 이전 state를 `runtime/restarts/takeover-*`에 보존하고 그 실행을 `failed/EXECUTION_ERROR`(중단, 결과 없음)로 기록하며 `orchestrator_session_id`를 현재 Codex session(`CODEX_THREAD_ID`)으로 옮긴다. 그리고 이전 입력과 이미 준 답을 이어받는 새 실행을 `--feedback`으로 예약해 `taken_over`가 붙은 `launch` 결과를 반환한다. 이후 `next.bind`·`next.finish`는 일반 stage와 같다. `Running stage cannot be verified stopped`이면 이전 대화를 닫거나 agent가 끝나기를 기다린 뒤 같은 명령을 반복하고, agent가 output을 이미 썼다는 거부에는 안내된 `finish`를 실행한다. 변경된 project 파일은 사용자에게 보여 주고 commit 또는 stash를 요청한다. 인계 단계만 실행하려면 `harness-prepare-input.mjs --stage-id <stage> --take-over-interrupted true`를 쓰며 출력의 `next`가 이어갈 명령이다.

기존 stage가 `running`으로 남아 사용자 답을 처리할 수 없으면, 답의 원문과 질문 ID를 보존한 채 해당 실행에 `harness-native-stage.mjs inspect --execution-id <execution_id>`를 실행한다. 반환된 실제 `agent_id`로 현재 CLI의 서브에이전트 상태와 결과를 확인한다. 아직 실행 중이면 그 agent를 기다린다. 완료 결과가 있으면 기존 실행의 `finish`를 먼저 호출하고, 실제 실패가 확인되면 오류 원문으로 `fail`을 기록한다. 검증된 현재 질문이 답을 기다리면 실제 답을 `--answer`로 전달한다. 실패한 실행에 대기 질문이 없으면 기존 입력·결과·답변을 보존하는 `--feedback` 재개에 실제 오류와 사용자의 답 원문을 전달한다. 질문이 이미 답변된 경우에는 중복 전달하지 않는다. 에이전트 상태를 확인할 수 없으면 상태 파일을 임의로 변경하거나 새 실행을 시작하지 않는다.

`inspect`의 `thread_id`는 Codex 부모 session의 실제 시작 기록이 하나로 확인될 때만 제공된다. 현재 CLI가 해당 스레드의 상태 조회를 지원하면 이 ID와 부모 session을 함께 대조한다. `observation`은 현재 worktree와 부모 session에 연결된 hook의 최근 시작·종료 관찰이다. 어느 값도 단독으로 조회 시점의 실시간 에이전트 상태나 성공·실패 판정은 아니며, 중복 또는 늦게 도착한 hook이 있을 수 있다. 현재 CLI의 native 도구가 실제 종료를 확인하기 전에는 이 값만으로 실행을 실패 처리하거나 재개하지 않는다.

Codex에서는 같은 부모 대화의 `collaboration.list_agents` 또는 `wait_agent` 결과에서 `inspect`의 agent ID와 일치하는 실제 상태를 먼저 확인한다. 반환된 ID가 `/root/<이름>`이고 저장된 ID가 `<이름>`인 경우에만 그 전체 경로를 사용한다. 사용 가능한 경우 같은 호스트의 `mcp__codex_tui__read_thread`로 부모 생성 기록에 대조된 `thread_id`와 마지막 turn 결과를 확인할 수도 있다. `running` 또는 `active`는 계속 기다린다. 실제 `completed`이면 `finish`, 실제 `failed`이면 오류 원문을 보존해 `fail`을 실행한다. `notLoaded`, 누락된 agent, 다른 호스트의 상태 또는 과거의 완료 기록은 현재 종료를 증명하지 않는다. Claude에서는 현재 부모 대화의 native agent 상태와 도구가 전달한 종료 결과를 확인한다. 같은 agent가 이후 재개될 수 있으므로 과거 task-notification과 시작·종료 hook 관찰만으로 현재 종료를 추정하지 않는다.

원래 Codex 부모 대화에서 `collaboration.list_agents`를 호출할 수 있으면, 그 도구가 반환한 JSON 객체 전체를 수정하지 않고 표준 입력으로 `node .codex/scripts/harness-native-stage.mjs reconcile --execution-id <execution_id>`에 전달한다. 준비기는 저장된 agent ID와 현재 부모 session을 대조하고, 종료 상태는 해당 자식의 마지막 turn 기록과 일치할 때만 반영한다. `running`이면 해당 agent를 기다리고, `unknown`이면 추측하거나 중복 실행하지 않는다. `completed`의 결과는 기존 `finish`와 같은 형식·보안 검증을 거치며, 실제 `failed` 또는 `interrupted`는 실패 사유를 기록한다. 유효한 output 파일이 없는 읽기 전용 agent는 host의 완료 응답 원문을 출력으로 사용한다. 형식 오류는 같은 agent에게 반환해 수정하게 한다. 사용자가 중단한 경우 `reconcile`로 재개하지 말고 실제 종료를 확인한 뒤 `cancel`을 사용한다. 다른 세션에서 host 목록을 만들거나 응답을 지어내지 않는다.

`finish` 성공은 형식 검증 후 정본 결과를 기록한다. 보안 경계, workspace·실행 ID, 실제 승인과 결과 참조의 검증은 그대로 적용한다. 반환된 status와 code에 따라 사용자 질문·리뷰·다음 stage로 전환한다. 질문의 원문과 실제 사용자 답을 보존한다. 사용자 요청으로 중단된 경우 늦게 도착한 결과로 진행을 재개하지 않는다.

실패나 사용자 답변 뒤 새로운 실행을 준비하면 이전 결과와 입력을 제공받은 새 서브에이전트가 이어간다. 다른 CLI의 세션 ID를 넘기지 않는다. 단계별 독립 리뷰와 실제 E2E의 별도 승인 및 역할 요구사항은 해당 GUIDE를 따른다.

사용자가 완료된 `to-ticket` 산출물이나 요구사항·전술 설계 stage의 문서를 고치라고 지시하면 `harness-prepare-input.mjs --feedback <사용자 지시 원문> --user-revision true`로 준비한다. 뒤 stage의 대기 질문은 그 지시로 대체되며 사용자 지시를 agent 판단으로 만들어 내지 않는다. 요구사항·설계 변경 뒤 독립 리뷰와 영향 ticket을 재검토한다.

실패한 stage와 사용자가 취소한 stage는 실제 종료가 확인된 뒤 같은 stage에 `--feedback`을 전달한다. `REVIEW_REQUIRED`는 실제 독립 reviewer 결과를 `--feedback`으로 돌려준다. 사용자 질문의 답은 실제 답만 `--answer`로 전달하며, 준비기가 만든 `answers.json`을 확인한다. 최종 E2E 실패의 구현 수정 승인과 E2E 재실행 승인은 별개다. 검증되지 않은 반환을 성공으로 바꾸거나 기존 상태를 직접 고치지 않는다.

## 상위 stage 되돌아가기

stage가 `blocked` / `DEPENDENCY_INCOMPLETE`를 반환하면 `result.owner_stage`(앞 stage 중 빈틈을 소유한 가장 앞 stage)와 `result.dependency_gap`(무엇이 비었는지)이 반드시 있다. `finish`는 이를 검사해 없거나 앞 stage가 아니면 `format_error`로 같은 서브에이전트에 돌려보낸다. 이 block은 사용자 결정이 아니므로 **사용자에게 묻지 않고** 다음 순서로 자동 진행한다. 업무 결정은 이 과정에서도 사용자 질문(`USER_DECISION_REQUIRED`)으로만 오며, orchestrator가 대신 답하지 않는다.

1. `finish`가 출력한 `next`의 명령 `node .codex/scripts/harness-native-stage.mjs launch --stage-id <owner_stage> --reopen-for <blocked execution_id>`를 실행한다. 다른 옵션은 함께 쓰지 않는다. 실행기는 해당 stage의 최신 결과가 `blocked` / `DEPENDENCY_INCOMPLETE`이고 그 `owner_stage`가 요청한 stage일 때만 허용한다(그 뒤 stage가 이미 시작됐거나 발행됐으면 거부).
2. 문서와 산출물은 되돌리지 않는다. owner stage는 `dependency_gap_result` 입력과 gap 설명을 feedback으로 받아 기존 산출물을 앞으로 고친다. owner 뒤에 이미 `completed`였던 stage와 block된 stage는 상태에 `stale`로 기록되어 `completed/OK`로 인정되지 않는다.
3. owner가 완료되면 `finish` 출력의 `next`가 남은 stale stage를 알려 준다. owner 다음 stage부터 block된 stage까지 `launch --stage-id <stage>`를 순서대로 실행한다(옵션 불필요, 실행기가 "상위가 바뀌었으니 기존 산출물을 갱신하라"는 안내를 자동으로 붙인다). 순서를 어기면 오류가 다음 stage를 가리킨다. `tracker-publish`·`tactical-code`는 stale 상태에서 시작할 수 없다.
4. 마지막 전술 설계 stage(`context-boundary`)가 다시 완료될 때 전술 gate가, `tactical-data`가 다시 완료될 때 design-freeze gate가 다시 한 번 실행된다. `to-ticket`은 이 되돌아가기를 쓰지 않는다: 확정된 설계만 나누며 설계 결함은 `DESIGN_NOT_FROZEN`으로 사용자에게 보고한다.
5. 같은 gap으로 owner를 되돌린 결과가 다시 같은 block이면 새 근거 없이 반복하지 않고 사용자에게 보고한다.

`--restart-requirements true`는 사용자가 명시적으로 롤백을 지시한 경우에만 쓰며 이 경로와 별개다.

`DEPENDENCY_INCOMPLETE` block 뒤 `PREVIOUS_RESULT_MISSING`·`RESTART_REFUSED`·order guard·user-revision 거부가 나오면 그 오류의 `next`가 이 경로를 가리킨다. `result.owner_stage`가 있으면 `launch --stage-id <owner_stage> --reopen-for <blocked execution_id>`, 없으면(이전 Harness가 기록한 결과) `launch --stage-id <blocked stage> --feedback 'Re-check the blocker and return owner_stage and dependency_gap naming the earlier stage that must change.'`로 block된 stage를 다시 실행해 owner를 반환받는다. 요약 문장에서 owner를 추정하지 않고, `--user-revision`·`--restart-requirements`를 쓰거나 사용자에게 기다리라고 말하지 않는다.
