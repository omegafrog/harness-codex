# stakeholder-analysis.md 템플릿

`docs/specs/<plan-set-id>/stakeholder-analysis.md`를 아래 형식으로 쓴다. 이 문서는 persona 기록(참여자, 후보 요구사항과 결정, 충돌, 요청 범위 밖 관찰)만 담는다. 사용자가 확정한 요구사항의 초안은 `requirements.md`에 쓰며 그 모양은 [requirements.md 템플릿](../../requirements-fix/references/template.md)이 정한다. 사람이 읽는 문서이므로 한국어로 쓰고 ID, JSON 키, 경로, CLI 명령은 원형을 유지한다. 해당 사항이 없는 절에는 `없음`과 이유를 적는다.

작성 규칙:

- 후보 요구사항은 `CAND-01…`로 번호를 매기고 요청 앵커를 요청 원문에서 그대로 인용한다. 결정 전에는 `결정`을 `대기`로 둔다. `결정` 값은 `채택`, `채택: <선택한 option>`(열린 선택), `기각`, `보류`, `보류(후속): <기다리는 질문·선택지>`(다른 질문의 답에 달려 있어 아직 묻지 않음; OPEN 행은 처리 `보류(후속)`, 근거에 대상)이다. 완료 때 `보류(후속)` 행은 없어야 한다. 이전 실행에서 `보류(후속)`였던 행은 재개에서 다시 질문(`대기`)하거나, `채택`·`기각`·`보류`와 그 행을 다룬 새 질문의 `question_id` 출처를 적거나, 기록된 답이 이미 무의미하게 만든 경우 `불필요 — <question_id>: <고른 선택지> 때문에 …`로 쓴다. 합친 질문 하나의 답은 그 질문이 다룬 모든 후보에 같은 출처로 적는다.
- `종류`는 persona의 `kind`를 옮긴다: `goal` 목표, `rule` 업무 규칙, `exception` 예외, `completion` 완료 조건, `actor` 행위자.
- `결정 출처`에는 결정을 준 사용자 답변의 `question_id`(`answers.json` 기준)를 적는다. 사용자가 선택지 대신 직접 쓴 문장은 `사용자 문구`로 표시하고 `내용`에 그 문장을 옮긴다. 에이전트 판단을 결정 출처로 쓰지 않는다.
- 요청이 이미 말한 범위를 되풀이하는 항목은 후보 표에 넣지 않는다. 그 범위는 `requirements.md`의 `업무 목적`에 근거 `요청 원문`으로 직접 쓴다.
- `requirements.md`의 `요구사항 초안`에는 `채택`한 후보, 확정한 업무 주체, 요청 원문이 말한 범위만 쓰고, 문장마다 근거 `CAND-xx`(요청 범위는 `요청 원문`)를 붙인다. `기각`·`보류`·`대기` 후보와 `요청 범위 밖 관찰`은 쓰지 않는다.
- 업무 주체 초안은 요청에서 고를 실제 대안이 없으면 묻지 않고 `확정`, 출처 `요청 해석(에이전트 제안)`으로 두어 승인 요약에서 사용자가 고치게 한다. 대안을 물었다면 답변 뒤 출처를 그 `question_id`로 바꾼다. 사용자가 고친 부분은 사용자 문구로 쓴다.
- `event-storming`이 낸 범위 밖 관찰은 이 문서의 `요청 범위 밖 관찰` 표에 제안자 `LENS-DOMAIN (event-storming)`, 요청 앵커 `-`로 더한다.
- 참여자 표에는 요청자 `REQUESTER`를 항상 넣는다. `### 요청 기능` 표에는 요청이 이름을 말한 기능을 모두 요청 원문 그대로 인용해 결정 `확정`, 출처 `요청 원문`으로 적는다. 요청 기능은 채택·기각·보류를 묻지 않고, 내용이 정해지지 않은 기능의 내용 질문 ID만 `내용 질문`에 적는다.
- `### 미확정 사실` 표(`ID | 구분 | 사실 | 바뀌는 동작 | 처리 | 근거`)에는 persona나 분석이 알 수 없다고 보고한 사실 중 권한·데이터·화면 동작·외부 연동을 바꾸는 것을 `OPEN-01…`로 적는다. 구분은 `이용 조건`·`권한`·`데이터`·`화면 동작`·`외부 연동`·`기타` 중 하나다. 누가 이 기능을 쓰는지와 로그인이 필요한지를 정하는 `이용 조건` 행은 항상 하나 이상 둔다(사용자에게 보이는 화면이 없으면 사유와 함께 `해당 없음`). 처리는 `미정`·`확정`·`해당 없음`이다. `확정`의 근거는 `요청 원문 "<요청의 정확한 부분 문자열>"`, `answers.json`·`<execution_id>:<n>` 답변 참조, 존재하는 문서 경로(`docs/…`, `CONTEXT.md`) 중 하나이고, `해당 없음`은 사유를 근거에 적는다. 행동을 바꾸지 않는 모름만 `요청 범위 밖 관찰`에 둔다. 이 표는 범위를 넓히는 데 쓰지 않는다. `action_required`이고 질문이 둘 이상이면 `- 추천 조합 시나리오:` 줄의 값이 비어 있지 않아야 한다. 실행기는 표 형식과 완료 때 `미정`이 없는지, 관찰 표에 권한·접근을 모른다는 행이 섞였는지를 검사한다.
- 요청 범위 밖 관찰에는 persona의 요청 앵커를 그대로 옮긴다. 앵커가 요청 원문에 있으면 범위 밖이 아니라 후보다. 실행기가 이 표와 요청 기능 표, 참여자 표의 `REQUESTER`를 검사한다.

````markdown
# Stakeholder 분석

- plan set: `<plan-set-id>`
- 상태: 결정 대기 | 확정

## 1. 요청 원문

> 사용자의 요청을 수정·요약 없이 그대로 옮긴다.

## 2. 판정

- 판정: 실행 | 생략
- 사유: 판정 이유 한두 문장.
- 근거: 생략이면 요청이 바꾸는 기존 승인 Spec 경로와 업무 단위, 새 행위자·권한이 없다는 확인, 충돌하지 않는 기존 규칙.

## 3. 참여자

| ID | 구분 | 역할 | 실행 | 선택 근거 |
|---|---|---|---|---|
| REQUESTER | 요청자 | 요청자 | 요청 원문 | 요청에 적은 기능은 요청자가 이미 정한 요구사항이다 |
| LENS-DOMAIN | 전문가 관점 | 도메인 전문가 | 실행 | 기본 관점 |
| LENS-SECURITY | 전문가 관점 | 보안 전문가 | 실행 | 기본 관점 |
| SH-01 | stakeholder | 역할 이름 | 실행 | 요청 문구 "…"가 이 카드의 목표 "…"와 닿는다 |
| SH-02 | 제약 출처 | 이름 | 제약 전달 | persona로 실행하지 않고 제약을 모든 persona에 전달했다 |
| SH-03 | stakeholder | 역할 이름 | 미선택 | 요청과 닿는 문구가 없다 / 상한 3을 넘어 제외했다 / 카드 형식 오류: 오류 메시지 |

### 요청 기능

요청이 이름을 말한 기능은 요청자(`REQUESTER`)가 정한 요구사항이다. 포함 여부를 묻지 않으며, 내용이 정해지지 않은 기능만 내용 질문을 한다.

| 요청 기능 | 요청 문구 | 제안자 | 결정 | 출처 | 내용 질문 |
|---|---|---|---|---|---|
| 커뮤니티 | "커뮤니티 기능" | REQUESTER | 확정 | 요청 원문 | `<execution_id>:4` |

### 미확정 사실

| ID | 구분 | 사실 | 바뀌는 동작 | 처리 | 근거 |
|---|---|---|---|---|---|
| OPEN-01 | 이용 조건 | 이 기능을 누가 쓰는지, 로그인이 필요한지 | 권한 검사와 화면 진입 | 확정 | `<execution_id>:5` |
| OPEN-02 | 데이터 | 삭제한 항목을 복구하는지 | 삭제 후 조회 결과 | 미정 | |
| OPEN-03 | 외부 연동 | 알림 발송 채널 | 알림 기능 | 해당 없음 | 요청에 알림이 없다 |

- 추천 조합 시나리오: 두 개 이상의 질문을 한 번에 물을 때, 추천 선택지를 모두 같은 구체적 상황에 적용한 한두 문장. 서로 모순되면 추천을 바꾸거나 의존 질문을 `보류(후속)`으로 미룬다.

## 4. 후보 요구사항

| CAND | 제안자 | 종류 | 내용 | 요청 앵커 | 근거 | 결정 | 결정 출처 |
|---|---|---|---|---|---|---|---|
| CAND-01 | LENS-DOMAIN, SH-01 | 업무 규칙 | 후보 규칙 문장 | "요청 원문 인용" | persona의 근거. 결정할 것만 말한 문장은 다시 써서 넣고 `원문: persona 문장`을 덧붙인다 | 채택 | `<execution_id>:1` |
| CAND-04 | LENS-DOMAIN | 업무 규칙 | 구체 규칙 A / 구체 규칙 B | "…" | … | 채택: 구체 규칙 A | `<execution_id>:3` |
| CAND-02 | LENS-SECURITY | 예외 | … | "…" | … | 기각 | `<execution_id>:2` |
| CAND-03 | SH-01 | 목표 | … | "…" | … | 대기 | |

## 5. 충돌

| 충돌 | 요청 앵커 | 입장 | 라운드 2 결과 | 결정 | 결정 출처 |
|---|---|---|---|---|---|
| CONF-01 | "요청 원문 인용" | CAND-03 대 CAND-05 | CAND-03 제안자: keep. CAND-05 제안자: concede | CAND-03 채택, CAND-05 기각 | `<execution_id>:6` |

충돌이 없으면 `없음`으로 쓴다.

<details>
<summary>요청 범위 밖 관찰 (참고용, 요구사항 아님)</summary>

|---|---|---|---|
````

## 생략 판정의 문서

`판정: 생략`이면 1절과 2절만 채우고 3~5절(`미확정 사실` 포함)은 `해당 없음 — 생략 판정`으로 쓴다. 근거에는 확인한 기존 Spec 경로를 적는다. 이 plan set에서는 `requirements.md`를 만들지 않고, 뒤따르는 requirements stage들은 생략을 결과 요약에 기록하고 문서를 쓰지 않는다.
