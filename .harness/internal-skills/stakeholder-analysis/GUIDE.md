# stakeholder-analysis

실행 배정에 `document_draft_root`가 있으면 완성한 문서를 그 아래의 같은 상대 경로에 직접 쓴다. 실행기가 gate 통과 후 그 바이트를 정본에 반영한다. 결과에는 정본의 상대 경로를 적는다.

## Purpose

First stage of a new feature: extract candidate requirements for the user's request from independent persona agents, and let the user adopt them one by one. Only adopted candidates enter the requirements. A candidate is a decision the request leaves open, never a restatement of the request. This stage is the facilitator: it selects personas, runs them, checks their output, finds conflicts, asks the user and records the result. The persona record stays in `stakeholder-analysis.md`; the requirements the user settled go into the living spec `requirements.md`, which this stage creates. It does not write the Product Spec; the stages from `subdomain-candidates` to `requirements-fix` continue the requirements.

## Inputs

- The user request (`scope` of the execution input), read verbatim. It is the only subject of discussion. The requester is a stakeholder (`REQUESTER`): every feature the request names is the requester's settled requirement.
- Any attached text reference explicitly named in the request (for example `첨부 파일: /path/to/requirements.md`). Read it before defining the requested-feature rows. It supplies the concrete capability anchors when the request gives only a broad goal.
- Default expert lenses: [domain expert](references/lenses/domain.md), [security expert](references/lenses/security.md).
- Registered stakeholder cards: `node .harness/scripts/harness-stakeholder.mjs list --json` in the active workspace. Cards are project-owned; never create, edit or remove them. A card under `problems` is malformed and is not run.
- The repository-root `<workspace_root>/CONTEXT.md` (not under `docs/specs/`), and an approved `docs/specs/*/product-spec.md` only for the skip decision.
- [Output template](references/output-template.md), the [requirements.md template](../requirements-fix/references/template.md) and the [persona contract](../stakeholder-persona/GUIDE.md).

## Prohibited

- Inspecting source or test code, or choosing frameworks, persistence or module structure.
- Turning actors named in the request into personas. Only registered cards become stakeholder personas.
- Treating a persona statement, or agreement among personas, as a user decision.
- Asking whether a feature the request names is in scope, or offering to reject, hold or defer it. Its content may be asked; its inclusion is settled.
- Treating a broad goal or project label (`RAG 개선`, `검색 고도화`, `서비스 구축`) as the complete feature breakdown when the request cites a source document with concrete capabilities.
- Excluding an anchored candidate for any reason other than its anchor (see step 6).
- Writing requirements the user has not adopted into the Product Spec or `CONTEXT.md`.

## Process

1. Use the active workspace as cwd. Return `blocked` when `context.workspace.preflight.valid` is false; take document paths from `context.workspace.documents`. Use those exact paths to check, read or write either file. Scope discovery under `docs/specs/` to `product-spec.md` candidates for the skip decision.
2. On resume, read the previous result, the existing `stakeholder-analysis.md`, `requirements.md` and the actual answers. Continue at step 10 when answers exist, otherwise at the first step whose output is not recorded. Never rerun personas whose output is already recorded unless the user revision changes the requested-feature inventory or explicitly asks to re-evaluate candidates against the request/source; then rerun each selected persona once with the current inventory and replace only candidate proposals, preserving decisions that still apply. A `--feedback`, recovery or takeover run (the input has `context.previous_result_ref` or an `input_refs` entry of `kind: previous_execution_result`) whose `stakeholder-analysis.md` holds a candidate table normally spawns no persona: reuse those rows and prior result refs. Spawn only a selected persona with no recorded candidates, one whose candidate output is stale under the exception above, or round 2 for a `CONF` the new input opens.
3. Skip decision. Skip only when all hold: the request changes behavior inside one use case of an existing approved Product Spec, adds no actor or authority, and conflicts with no existing business rule. When in doubt, run. For a skip, write only `stakeholder-analysis.md` with `판정: 생략`, the reason and the evidence paths, create no `requirements.md`, then return `completed/OK`. The later requirements stages then record the skip without writing and the tactical design stages run as before.
4. Extract requested features before persona selection or execution. If the request says to improve/build something based on an attached reference, read the referenced text and split it into distinct, observable capabilities or user outcomes; do not use the umbrella goal as the only feature. Keep the original request verbatim in section 1 and treat the broad phrase as goal/context. Record each adopted capability as a `REQUESTER` / `확정` row with its exact source phrase and `<absolute path>:<1-based line>`. Do not turn examples, alternatives or explanations into scope unless the request adopts them. If the source contains unresolved alternatives, ask a feature content question rather than choosing one. If an explicitly named attachment is inaccessible, ask the user for an accessible copy and do not invent the breakdown. Without attached material, list the concrete features named in the request as before.
5. Select personas: both default lenses always. The requester is always a participant (`REQUESTER`, 구분 `요청자`, 실행 `요청 원문`) and is never run as a persona. Add a registered `person` card only when its goals or pain points touch a phrase in the request or the settled requested-feature inventory; record that phrase as the selection reason. A `constraint-source` card is not run; pass its constraints to every persona as context and list it as a participant. Run at most 3 personas. When more cards qualify, keep the ones whose goals touch the request and its feature inventory most directly and record the rest, and any malformed card with its problem message, as not selected with the reason.
6. Round 1. Use `context.workspace.persona_binding` (model, reasoning effort) of the input. Only when it is absent run `node .harness/scripts/harness-stage-runtime.mjs binding --root <workspace_root> --skill stakeholder-persona` and use its result; if that fails, return `blocked` / `MODEL_BINDING_UNAVAILABLE`. Start one fresh native `stakeholder_persona` subagent per persona in parallel (Codex: `spawn_agent` with `fork_turns: "none"`; Claude Code: `Agent` with `subagent_type: stakeholder_persona`). Send each only its card text, constraint-source context, original request verbatim, and the settled requested-feature inventory. For every attached-source feature include its exact quoted phrase, absolute path and line, plus only the surrounding excerpt needed to understand the capability. Tell personas that the listed features are already in scope: do not ask which feature to prioritize or whether to include it; find only unresolved decisions that materially change how a listed feature works. Personas must not see each other's output. Wait for all of them.
7. Check every candidate:
   - A candidate anchor must exactly quote either the request or a phrase in the attached-source feature inventory. For an attached-source anchor, keep its absolute path and 1-based line in the candidate rationale/evidence. If it quotes neither, move it to `요청 범위 밖 관찰` with the anchor (reference only, never asked or adopted). This is the only reason a candidate leaves the candidate table: a decision about how a requested feature works stays a candidate; a candidate that merely repeats the feature itself is omitted because that scope is already settled. The runner rejects an observation anchored in the request or an adopted source feature.
   - An unknown a persona reports (target users, login, who may see or change, data, screen behavior, external integration) is an `OPEN-nn` row of the `미확정 사실` table when it changes permission, data, screen behavior or external integration, never an out-of-scope observation. An unknown that changes no behavior stays an observation. An OPEN row is not a feature: never use it to add scope. Keep one `이용 조건` row (who may use or see the feature): it matters only for a feature people use directly, so mark it `해당 없음` with a reason when nobody operates it directly (a scheduled job, an automatic notice, a batch). Ask it as who may use or see the feature, never as a login choice. Settle a row from the request (`확정`, 근거 `요청 원문 "<exact substring>"`), a recorded answer or an existing document before asking it; the rest are `미정`.
   - Drop a candidate that only restates the request's explicit scope, meaning it adds no decision beyond the request's words. It gets no `CAND` and no question; step 10 records that scope.
   - Merge candidates that state the same requirement; keep every proposer.
   - Assign `CAND-01…` in proposal order and keep the persona's rationale. Keep the persona's statement only when it is a complete rule or an open choice with concrete `options` (see the persona contract). A candidate whose statement only defers (ends in 정한다, 결정한다, 명확히 한다, 확인한다, 구체화한다 or the like) is a deferring candidate: rewrite it yourself into 2-3 concrete, mutually exclusive options from the request's wording (one observable outcome each, none that leaves the outcome to the implementer), keep its proposers, and record the persona wording as `원문: …` in the 근거 or 비고 cell when the table has room. A deferring candidate is never asked as adopt/reject/hold.
   - An observation about personal data, location or who can see data is an OPEN row even when the persona did not phrase it as unknown.
8. Round 2, only when two anchored candidates on the same request/source anchor contradict each other: give each involved persona the opposing candidate with a `CONF-nn` ID in its own subagent and ask for `keep`, `concede` or `revise`. If that subagent can no longer be continued, start a fresh one with its card, the request, its own round-1 candidates and the opposing candidate. Record the replies. Do not start a group discussion.
9. Write `stakeholder-analysis.md` from its template, and create `requirements.md` from the [requirements.md template](../requirements-fix/references/template.md) with the header and a `### 요구사항 초안` holding one `업무 목적` line per extracted requested feature, using its exact `요청 문구` and source citation (`요청 원문` or the attached `<path>:<line>`), plus the actor draft. Then ask in one batch: one question per `미정` OPEN row (recommended option and reason, like every question), one per anchored candidate, one per unresolved conflict (each side, or reject both), one content question per requested feature from step 4, and one for the business actor draft only when the request supports at least two concrete actor sets as options (never an edit or direct-input option such as `수정이 필요함`). When only your draft exists, do not ask: record the draft actors as `확정` with source `요청 해석(에이전트 제안)` and show them in the approval summary so the user can revise them. Ask what the feature does first. When a requested feature's content is open, the batch holds its content question, the access question and only questions that stand whatever those two answers are. A candidate that presupposes one content answer (for example, in a settlement feature, that users may correct closed months) is `보류(후속): <question id or option it waits on>` and is asked when the stage resumes. Ask only what the [asking criterion](../grilling/GUIDE.md#decide-whether-to-ask) makes `high`; a `low` decision is decided by you, sourced `요청 해석(에이전트 제안)`, and shown in the approval summary. No other question presupposes a capability that no settled rule or option of the content question provides. Declare `excludes` on every option that cannot hold with an option of another question (for example a notice sent to "the requester only" with one sent to "the requester and the approver's manager" cannot both be the recipient rule), and write the `- 추천 조합 시나리오:` line of the template. If the recommended options contradict each other, change a recommendation or defer the dependent question. Before asking, merge into ONE question every candidate, content question and OPEN row that asks the same fact: its title names all proposers and IDs (`CAND-xx`, `OPEN-xx`) and the answer settles all of them. A question that exists only under one answer of another question is not asked now: record its candidate (or OPEN row, 처리 `보류(후속)` with the target in 근거) as `보류(후속): <the question or option it waits on>`, and ask it after that answer when the stage resumes. A candidate that is a complete rule is asked as `채택` / `기각` / `보류`; an open choice (a persona's, or your rewrite of a deferring candidate) is asked with its concrete options as the options, and the decision is recorded as `채택: <option label>`. Write the questions in Korean and quote the request/source anchor. Start each question title with the stakeholders it came from, each by the role and ID of the participant table, for example `[제안: 도메인 전문가(LENS-DOMAIN), 결제 담당자(SH-01)]`: every proposer of a merged candidate, each side's proposers for a conflict, `[제안: 요청자(REQUESTER) · 요청 기능: <기능>]` for a content question of a requested feature, and `[제안: 요청 해석(에이전트)]` for a business actor question. A candidate that refines a requested feature also names that feature after its proposers (`· 요청 기능: <기능>`). Give each question a recommended option (per the criterion: the smallest option that serves the request's purpose, not merely the smallest) and a rationale grounded in the request/source, in the [question format](../grilling/GUIDE.md#ask-questions-the-user-can-answer): the request/source anchor and settled facts as context, and under each option its effect and an example of what it does to that feature. Every example applies the same concrete situation to its option. No option may leave the outcome to the implementer (`임의로`, `나중에 정함`, `후속 단계에서 다시 묻기`); only a `보류` option may say it is asked again later. Every question carries a one-line reason for its recommended option in `rationale`. For the access question (`이용 조건`) recommend from evidence: request/source wording and the project's existing access rules; when there is none, recommend the smallest option that still serves the purpose as a user of such a feature would expect, and name that purpose in `rationale`. Recommend an option that requires a login only when `rationale` cites evidence of an existing login: request text about login/member/auth or an existing project file path about login/auth (not a Harness-owned file); the executor rejects it otherwise. When no question exists, return `completed/OK` without asking. Return `action_required` / `USER_DECISION_REQUIRED`.
10. With the actual answers, record each decision (`채택`, `채택: <option>`, `기각`, `보류`; the one answer of a merged question goes on every candidate it covers) and its `answers.json` source in `stakeholder-analysis.md`, ask every `보류(후속)` row on resume: put it in a new batch (`대기` while asked, its ID in the question title) and return `action_required` again, never `completed` and never a plain `보류` or a dropped row without asking. Only an answer already recorded can make it moot: write `불필요 — <question id>: <chosen option> 때문에 …` in its 결정 (OPEN row: 처리 `해당 없음`, 근거). The runner rejects completion while a row is `보류(후속)` (`DEFERRED_QUESTION_PENDING`) and a row that was `보류(후속)` in the published analysis and is settled without a recorded answer about it (`DEFERRED_QUESTION_DROPPED`), and write each answered OPEN row back as `확정` with that source (the `<execution-id>:<n>` question id). A `미정` row cannot be completed. When the table is missing from an analysis written before it existed, do not add it on resume. Complete the `requirements.md` draft only from adopted candidates (an adopted option becomes the rule), content answers, confirmed actors and the request's own scope: `업무 목적` with one line per requested feature (source `요청 원문`, `REQUESTER`), `업무 주체`, `참여한 stakeholder` including `REQUESTER`, and draft normal and exception scenarios, each with its source, plus the header's `참여한 stakeholder`. Every requested feature has at least one draft scenario from its content answer or an adopted candidate. A draft line that states the outcome of a `확정` OPEN row (at least the `이용 조건` row) cites that OPEN id in its source, e.g. `출처: CAND-02 채택, OPEN-01, answers.json <question_id>`; the runner rejects a completed result whose requirements.md never cites it. A free-text answer that changes a candidate is recorded as the user's wording. Ask again only when an answer is ambiguous. Return `completed/OK` with both artifacts.

## Completion

- `stakeholder-analysis.md` exists at the resolved path, lists every participant and selection reason, and every anchored candidate has a user decision with its source. It holds no requirement draft.
- The requested-feature table lists every concrete capability the request asks for, including capabilities extracted from any cited attached source, as `REQUESTER` / `확정`; its exact quote and source path are recorded. A broad goal alone does not satisfy a multi-capability reference. The participant table lists `REQUESTER`. The runner checks these citations, the `미확정 사실` table (an `이용 조건` row, sources, no `미정` row at completion, no access unknown filed as an observation) and that no observation anchored in the request was moved out of scope.
- `requirements.md` exists with `상태: draft`, and its `요구사항 초안` has one purpose line per extracted feature and cites only adopted candidates (`CAND-xx`), content answers, confirmed actors, the request text or attached source line, with a draft scenario for every requested feature.
- Rejected and held candidates stay in the candidate table and are not reintroduced by later stages without a new user decision.
- The runner commits `docs/specs/<plan-set-id>/` when this stage completes. `subdomain-candidates` continues from both documents.

## 공통 도메인 조회

입력의 `domain_context_pack`이 있으면 필요한 후보부터 확인한다. 상세는 `node .harness/scripts/harness-domain.mjs get <ID>...`로 일괄 조회하고 후보가 부족하면 `discover` 또는 `search`로 범위를 넓힌다. 기존 Actor·권한·규칙과 같은 결정을 다시 묻기 전에 정본을 비교한다. persona 입력 계약은 유지한다.
