# to-ticket

실행 배정에 `document_draft_root`가 있으면 문서별 결정·근거·변경 위치와 필요한 양식을 그 아래의 같은 상대 경로에 간결하게 모은다. 완성 문장은 작성 에이전트가 한 묶음으로 작성한다. 아래의 작성·수정 지시는 작성 에이전트에게 넘길 내용 기준으로 사용하고, 결과에는 정본의 상대 경로를 적는다.

정본 계획을 만들기 전에 이 stage의 작업자가 `node .harness/scripts/harness-native-stage.mjs draft-ready --execution-id <execution_id> --agent-id <agent_id>`를 실행한다. `writer_required`이면 반환된 `agent_profile`과 `binding`으로 fresh 작성 에이전트 한 명을 시작한다(Codex `fork_turns: "none"`). `next.bind`에 실제 writer ID를 넣고 `writer_brief_path`와 `write_command`만 전달한다. 본문은 전달하지 않는다. 작성 에이전트가 끝나면 `next.finish`에서 `review_ready`를 확인한다. 같은 stage 작업자가 이어서 `harness-native-command.mjs`로 계획 검사를 호출하고 완성된 실행 초안을 독립 reviewer에게 맡긴다. 검토가 통과하면 보통의 `receive_command`로 결과를 제출한다. 실행기는 리뷰된 바이트를 한 번만 정본에 반영한다. 미검토 변경안을 내는 수정 회차는 같은 절차로 검토한다.

`execution_id`를 받은 호출은 해당 stage 파일에 지정된 작업을 수행하고 결과 파일과 공통 envelope를 반환한다.

## Plan authoring stage

The canonical entrypoint is `.harness/internal-skills/to-ticket/GUIDE.md`, already supplied by the runner. Do not require or search for a public `skills/to-ticket/SKILL.md` copy. `AGENTS.md` and `.harness/agents/EXEC.md` provide project guidance when present; their absence or empty content is not a plan-authoring prerequisite. Do not return `DEPENDENCY_INCOMPLETE`, invoke setup, or create filler guidance solely for those files. Preserve the actual workspace identity, the settled tactical design and decision documents, decision evidence and planning gates. Describe necessary implementation/runtime preparation in the tickets; actual service/E2E launch readiness is checked when that execution begins.

The static runner supplies `context.execution_workspace`. Do not author workspace paths or branch metadata in tickets or tracker drafts; the publication input preparer generates execution metadata and body file paths.

`to-ticket` owns ticket authoring and its independent review loop. It runs only after all tactical design stages and the decision stages (`tactical-technology`, `tactical-ui`, `tactical-api`, `tactical-data`) completed and the design is frozen (the design-freeze gate passed), and before the user approves publication. It adds no scope and asks no scope question. If ticket decomposition exposes a missing or contradictory earlier design decision—including a decision the user supplied after the freeze—return `blocked/DEPENDENCY_INCOMPLETE` with the earliest owning prior `owner_stage` and a concrete `dependency_gap`; the orchestrator reopens that owner and reruns stale stages in order. Do not edit another stage's design document from to-ticket. Use [split](references/split.md) on the initial invocation and [revision](references/revision.md) to address findings. It calls a fresh native `plan_reviewer` subagent itself, records the attempt through `harness-plan-review.mjs`, revises the tickets when needed, and repeats with a different fresh reviewer. It returns `completed/OK` only after `check --phase planning` confirms the canonical review is current and passing. Plan review is never handed to the main orchestrator as `REVIEW_REQUIRED`; actual user decisions use `USER_DECISION_REQUIRED`.

Before splitting, check that `technology.md` settles every applicable implementation stack item required by the tactical-technology GUIDE, including runtime/language, applicable framework, persistence client, and test CLI. If a necessary choice is absent or unresolved, return `blocked/DEPENDENCY_INCOMPLETE`, name `tactical-technology` as `owner_stage`, and describe the missing decision in `dependency_gap`; do not invent a stack, publish tickets, or defer the choice until implementation.

When the user explicitly asks to restart a waiting or failed `to-ticket` stage from its settled inputs, prepare a fresh stage input with `node .harness/scripts/harness-prepare-input.mjs --worktree-ref <canonical-worktree.json> --stage-id to-ticket --restart true`. The runner accepts this only in the active matching worktree while tracker-publish has never started. It archives the prior plan set, review history, and `runtime/to-ticket` artifacts under `.io/runtime/restarts/`; execution history and the design documents remain in place. Never use restart to bypass a running stage or reviewer.

- Write canonical tickets from the settled design, then execute the review loop in this stage. A ticket carries a rule at the precision of `requirements.md` and `tactical-design.md` and never adds or tightens one. For every task and dependency, name the INV/EX/AC, BIZ or `tactical-design.md` bounded-context boundary rule that would fail without it. Convention and future convenience do not justify extra work; omit optional additions without asking about them. Ask the user only when a necessary decision cannot be resolved from the design and decision documents.
- The Git ignore preparation in [split](references/split.md) is a required implementation environment baseline; it does not add a product requirement.
- A `revise` verdict causes a scoped ticket revision and a new attempt with a new reviewer. Preserve the configured three substantive-attempt limit; after it is reached, return the concrete unresolved decision to the user. User answers do not count as a review pass.
- Before authoring, use `context.worktree_ref`, `context.plan_set_id`, and the exact design paths in `input_refs`. Open those paths directly. Read the requirements for scope and read only the tactical-design sections needed to split the approved BIZs, following [split](references/split.md). Open a frontend brief only when `input_refs` supplies it. If a required document is missing, report its canonical path.
- Keep every ticket vertical, with explicit dependencies, inside the plan-set boundary. Preserve approved decisions and stable IDs. A rule the tickets need but `requirements.md` lacks is not added in a ticket: return `SPEC_REVISION_REQUIRED` so the requirements are reopened first. A design defect (a BIZ without an owning model, an endpoint that traces to no requirement, a context relation without a boundary decision, or an outbound interface without a concrete binding) is never fixed in a ticket. Return `blocked/DEPENDENCY_INCOMPLETE` with the earliest prior stage that owns the missing design (`owner_stage`) and evidence naming the canonical document, item, requirement ID, and the user decision or contradiction that exposes the gap (`dependency_gap`). Leave the design document untouched. The design-freeze gate prevents known incomplete designs from starting to-ticket; this path handles gaps found during decomposition or decisions recorded after that gate passed. The orchestrator reopens the named owner, reruns affected stages and to-ticket in order, and does not ask the user to repeat an already settled decision. Use `INPUT_MISSING` only when no prior stage can be identified as owner and the missing input is not a business decision for the user to make. Ticket changes that do not require a design change stay within this stage.
- For frontend visual acceptance criteria that require real browser zoom, set `requires_real_zoom: true` in the ticket's YAML frontmatter next to `frontend: true`; that key is the explicit signal the browser preflight reads (`requires_real_zoom: false` quotes a zoom phrase without asking for a headed display). Without the key, state the browser and scale explicitly in the criterion (for example, `브라우저를 200%로 확대`). Bare percentages or unscaled browser-zoom mentions can describe content/image magnification or out-of-scope behavior and do not establish a headed-browser requirement.
- Use the configured tracker helpers or connector; do not handcraft API payloads or duplicate canonical tracker state. Report created or rendered artifacts, dependency/resource evidence, validation results and blockers.
- Do not run Git: when the stage completes and its result is accepted, the runner commits the plan documents under `docs/plans/<plan-set-id>/`. The Issue drafts below are session files and are not committed.
- GitHub tracker mode에서는 [GitHub 양식](references/github-issue-template.md)에 맞출 상위 Issue와 하위 Issue별 요점을 `document_draft_root`의 형제 `session/runtime/to-ticket/drafts/parent.md`와 `session/runtime/to-ticket/drafts/<plan-id>.md`에 모은다. 하나의 writer 배정에 계획과 Issue를 함께 넘긴다. writer가 작성한 Issue 텍스트는 완료 시 `<session_directory>/runtime/to-ticket/drafts/`에 저장한다.
- Save these drafts before `harness-plan-review.mjs begin`; admission and `check --phase planning` validate them as well as the final result. Missing drafts are preparation work, not a user decision or a reason to rerun an unchanged passing review. Complete the drafts and rerun the planning check when the reviewed snapshot is unchanged.
- A `pass` verdict completes plan authoring only after the current snapshot check. The orchestrator then shows the whole reviewed plan set to the user and asks whether to publish it; only the user's own reply starts the separate `tracker-publish` workflow stage. This skill never publishes to the tracker.

The following publisher is a separate workflow stage, not a nested subagent or an action performed by the orchestrator main session. It owns tracker publication and returns the final receipt. `tactical-code` implements the published tickets one at a time afterwards.

The orchestrator presents real user questions and preserves actual answers. A user answer resolves only the asked decision; it does not make a review pass. Standalone use follows the same split → internal independent review → revision when needed and completion gate.
