# requirements-fix coverage checklist

`requirements-fix`가 인터뷰 전과 인계 전에 `requirements.md`의 BIZ와 공통 섹션을 확인하는 목록이다. `bounded-context`는 요구사항을 확정하기 전에 전체를 확인한다.

- `SETTLED`는 요청·채택 후보·사용자 답변·해결된 hotspot이나 근거를 기록한 합리적인 기본값으로 정해진 항목이다.
- `PARTIAL`은 일부가 정해졌지만 결과에 영향을 주는 결정이 남은 항목이다.
- `UNRESOLVED`는 필요한 동작이나 결정이 아직 정해지지 않은 항목이다.
- `NOT_APPLICABLE`은 해당하지 않는 항목이다. 구체적인 이유를 적는다.

## BIZ마다 분류하는 행

| 필드 | `SETTLED`인 경우 | 비어 있을 때 묻는 것 |
|---|---|---|
| 업무 목적 | 누구에게 어떤 결과를 주는지가 요청 원문, 채택 후보, 사용자 답변에 있다 | 요청 범위가 갈릴 때만 묻는다. 이유가 따로 없다는 것만으로 묻지 않는다 |
| 업무 주체 | 행위자마다 만들기·보기·고치기·지우기 권한이 정해졌다 | 정해지지 않은 행위자별 권한 |
| 조회 행위 | 사용자가 현재 상태를 봐야 하는 행위(예: 바꾸기 전에 현재 값 확인)마다 조회가 정해졌거나 필요 없는 이유가 있다 | 어떤 조회가 필요한지 |
| 독립적으로 완료되는 업무 | 요청·채택 후보·답변에 근거한 독립 완료가 각 BIZ로 추적된다. 다른 업무의 정책·규칙·예외에 포함된 별도 완료도 해당한다 | 독립 업무가 누락되면 `subdomain-candidates`에 출처와 빠진 업무를 전달한다 |
| 대상 데이터 | BIZ가 다루는 데이터가 무엇인지와 누가 소유하는지가 업무 말로 정해졌다. 필드·형식·Aggregate 구성은 `domain-model`이 정하므로 묻지 않는다 | 데이터가 무엇이고 누구 것인지 |
| 사용자에게 보이는 정보 | 사용자가 업무 결과로 보거나 받는 정보 항목이 정해졌다. 응답 JSON 모양은 묻지 않는다 | 사용자에게 보여 줄 정보 항목 |
| 선택·판정 조건 | 대상을 고르거나 맞는지 판정하는 규칙(속한다·겹친다·가깝다·맞는다 …)마다 관찰 가능한 경계 조건이 적혔다 | 구체적인 일치 조건 |
| 정상 시나리오 | 시작 조건, 단계, 끝 상태가 이어지고 이벤트 흐름 표와 어긋나지 않는다 | 끊긴 단계, 끝 상태 |
| 업무 규칙 | 수치·길이·경계·형식과 삭제 전파가 정해졌다 | 결과를 바꾸는 값과 전파 범위 |
| 예외 시나리오 | 흐름이 정상으로 끝나지 않는 경우와 그때의 업무 결과가 정해졌다 | 거절·중복·빈 결과·취소의 결과 |
| 완료 조건 | 정상 시나리오·규칙·예외마다 관찰 가능한 `AC`가 하나 이상 있다 | 관찰 가능한 기준이 없는 항목 |
| 이벤트 흐름 | `event-storming`의 hotspot이 모두 `해결`이고 정책이 규칙·예외와 모순되지 않는다 | 남은 hotspot |

## 문서 공통 행

| 항목 | `SETTLED`인 경우 | 비어 있을 때 묻는 것 |
|---|---|---|
| 범위·비목표 | 포함은 요청 원문과 확정 항목으로 추적되고, 제외는 요청이 하지 않는 일로 적혔다 | 포함 여부가 갈리는 경계 |
| 우선순위·트레이드오프 | 업무끼리 충돌하는 경우가 없거나 앞서는 쪽이 정해졌다 | 충돌할 때 앞서는 업무 |
| 업무 상태·전이 | 상태를 가진 대상마다 상태와 전이가 정해졌다. 상태가 없으면 `NOT_APPLICABLE` | 빠진 상태·전이 조건 |
| E2E 시나리오 | 핵심 BIZ를 끝까지 따라가는 흐름이 있고 모든 단계가 INV·AC·BIZ에서 나온다 | 시나리오에 필요한데 요구에 없는 동작을 넣을지 |
| 서브도메인·바운디드 컨텍스트 | SD 표가 `confirmed`이고, 분류와 묶음 경계가 각각 사용자 결정으로 추적되며, 모든 BIZ가 `### 1.1` 표의 컨텍스트 하나에 속한다. SD는 앞선 stage에서 사용자가 정했으므로 다시 묻지 않는다. 컨텍스트 소속은 `requirements-fix` 뒤에 `bounded-context`가 정하고 이 행을 확인하므로 `requirements-fix`는 분류하지 않는다 | 표에서 빠진 BIZ |
| 용어 | 문장이 `## 3` 용어 표의 말만 쓰고, 컨텍스트마다 뜻이 다른 말은 컨텍스트별 줄이 있다 | 표에 없는 새 혼용어의 뜻 |
| 서브도메인 간 이벤트 | `## 4` 표의 받는 쪽 반응이 받는 BIZ의 규칙·예외와 맞는다 | 반응이 정해지지 않은 이벤트 |

## 확정 조건

- 모든 행이 `SETTLED` 또는 `NOT_APPLICABLE`이다.
- 사용자 결정으로 쓴 항목은 요청 원문, 채택 후보, `answers.json`, 사용자 수정 지시 중 하나를 출처로 갖는다. 에이전트 제안 항목은 그렇게 표시되어 있고 요청 범위를 넓히지 않는다.
- 채택한 `CAND`는 모두 어느 BIZ 항목으로 들어가 있다. 기각·보류·`요청 범위 밖 관찰`은 들어와 있지 않다.
- `INV`와 `EX`마다 이를 확인하는 `AC`가 하나 이상 있다.
- `PARTIAL`·`UNRESOLVED`로 판정한 BIZ 행은 기존 근거나 기록한 합리적인 기본값으로 정할 수 없으면 모두 한 번의 질문 묶음에 들어간다.
- 결과가 대상을 고르거나 판정하는 표현(예: "속하는"·"적절한"·"관련된")에 달린 `AC`는 경계 조건(값·범위·판정 규칙)이 같은 BIZ의 `INV`나 `AC`에 적혀 있기 전에는 `SETTLED`가 아니다.
- 서로 모순되는 항목, 단위·정밀도를 사용자가 말하지 않았는데 끼워 넣은 문구가 없다.

## 작성기 검증 규칙

아래 규칙은 `requirements.md`를 작성하는 requirements stage가 gate에 제출하기 전에 직접 확인할 형식·내용 요건이다. 각 BIZ 절 안에서 확인하며, 다른 BIZ나 문서 공통 절에 쓴 문장으로 대신하지 않는다.

### 업무 규칙 (`INV`)

- 각 규칙은 안정 ID(`INV-xx`)와 실제 규칙을 포함한다. `없음`, `후속 stage가 채운다`, 주제만 적은 문구는 완료된 규칙이 아니다.
- 규칙이 적용되는 시나리오가 있으면 `[SC-xx]`로 연결한다. 사용자 결정이나 계약에서 규칙을 추적할 수 있게 출처를 기록한다.

### 예외 시나리오 (`EX`)

- 해당 BIZ의 예외 시나리오마다 안정 ID(`EX-xx`)를 붙인다. 각 항목은 예외가 발생하는 구체적인 조건과 실제 규칙, 업무 결과 또는 관찰 가능한 조건을 설명해야 한다. `EX-xx 오류를 알린다`처럼 발생 조건과 결과를 확인할 수 없는 요약은 충분하지 않다.
- 가능한 경우 영향받는 정상 시나리오(`[SC-xx]`)를 연결하고, 출처를 기록한다.
- 예외가 적용되지 않는 경우에는 그 BIZ의 `예외 시나리오` 필드에 안정 ID(`EX-xx`), `NOT_APPLICABLE`, 실제 근거가 되는 규칙·결과, 그리고 구체적인 이유를 함께 적는다. 예: `EX-07 [SC-01] NOT_APPLICABLE — 조건: …; 결과: …; 별도 실패·거절 경로가 없는 이유: …`. 이 항목은 예외 경로를 새로 만들지 않고 해당 BIZ에 예외가 없다는 판정과 확인 근거를 추적한다. `예외 없음`만 적거나 다른 BIZ의 예외를 가리키지 않는다.
- 한 BIZ에 실제 `EX`가 있더라도 별도의 실패·거절 경로가 적용되지 않는다고 판단하면, 두 내용을 각각 분명히 쓴다. 실제 EX 항목에 안정 ID와 조건·결과를 부여하는 것으로 `NOT_APPLICABLE` 설명을 대체할 수 없고, 반대도 마찬가지다.

### 완료 조건 (`AC`)

- 각 정상 시나리오와 `INV`·`EX`를 관찰 가능한 완료 조건(`AC-xx`)에 연결한다.
- 각 AC에는 적용 조건, 행위, 관찰 가능한 결과를 쓴다. 데이터 상태가 보존·변경되는 것이 업무 결과에 중요하면 그 상태도 명시한다.
- AC가 참조하는 모든 `SC`·`INV`·`EX` ID는 같은 BIZ에 실제로 정의되어 있어야 한다. 정의되지 않은 ID를 만들거나 다른 BIZ의 항목으로 연결하지 않는다.

### 제출 전 점검

- 현재 upstream 결과를 다시 읽고, 수정 전 결과를 그대로 제출하지 않는다. stage 재개 또는 gate 반려 후에는 최신 사용자 답변과 소유 stage 산출물을 기준으로 각 관련 BIZ를 다시 대조한다.
- 모든 BIZ의 `업무 규칙`, `예외 시나리오`, `완료 조건`이 각 한 번만 나타나며, 빈칸용 placeholder가 남지 않았는지 확인한다.
- 위 조건을 충족하지 못하면 gate 통과를 가정해 `completed/OK`로 반환하지 말고, 미확정 사용자 결정은 질문으로, 소유권이 앞선 항목은 해당 owner의 dependency로 반환한다.
