# requirements-fix coverage checklist

`requirements-fix`가 인터뷰 전과 인계 전에 `requirements.md`의 BIZ와 공통 섹션을 확인하는 목록이다. `bounded-context`는 요구사항을 확정하기 전에 전체를 확인한다.

- `SETTLED`는 요청·채택 후보·사용자 답변·해결된 hotspot이나 근거를 기록한 합리적인 기본값으로 정해진 항목이다.
- `PARTIAL`은 일부가 정해졌지만 결과에 영향을 주는 결정이 남은 항목이다.
- `UNRESOLVED`는 필요한 동작이나 결정이 아직 정해지지 않은 항목이다.
- `NOT_APPLICABLE`은 해당하지 않는 항목이다. 구체적인 이유를 적는다.

## BIZ마다 분류하는 행

| 추적 | `SETTLED`인 경우 | 비어 있을 때 소유자 |
|---|---|---|
| 요청 범위 | 요청 기능은 모두 명시적으로 포함되고 모든 ACT가 포함·제외·후속 중 하나이며 근거/answer ID가 있다 | scope 판단은 `stakeholder-analysis` |
| 행동 ↔ BIZ | 포함 ACT마다 BIZ 링크가 있고 모든 BIZ가 ACT와 근거로 돌아간다 | 누락된 독립 업무/BIZ는 `subdomain-candidates`; 누락된 scope 결정은 `stakeholder-analysis` |
| 시나리오 분기 | 정상, 유효 대안, 실패/거절을 검토하고 관련 경로마다 SC 또는 이유 있는 `NOT_APPLICABLE`가 있다 | 경로 발굴은 `event-storming`; 미정 정책/결과는 `requirements-fix` |
| 시나리오 ↔ AC | 각 SC와 적용 가능한 INV/EX는 조건·행위·관찰 결과·상태 결과를 가진 AC에 명시 연결된다 | AC의 업무 기준은 `requirements-fix` |

| 필드 | `SETTLED`인 경우 | 비어 있을 때 묻는 것 |
|---|---|---|
| 업무 목적 | 누구에게 어떤 결과를 주는지가 요청 원문, 채택 후보, 사용자 답변에 있다 | 요청 범위가 갈릴 때만 묻는다. 이유가 따로 없다는 것만으로 묻지 않는다 |
| 업무 주체 | 이 BIZ에 적용되는 행위자와 실제 필요한 권한이 정해졌다 | 결과를 바꿀 권한 경계가 남은 경우에만 묻는다. 적용되지 않는 만들기·보기·고치기·지우기를 가정하지 않는다 |
| 독립적으로 완료되는 업무 | 요청·채택 후보·답변에 근거한 독립 완료가 각 BIZ로 추적된다. 다른 업무의 정책·규칙·예외에 포함된 별도 완료도 해당한다 | 독립 업무가 누락되면 `subdomain-candidates`에 출처와 빠진 업무를 전달한다 |
| 정상 시나리오 | 시작 조건, 단계, 끝 상태가 이어지고 이벤트 흐름 표와 어긋나지 않는다 | 끊긴 단계, 끝 상태 |
| 업무 규칙 | 수치·길이·경계·형식과 삭제 전파가 정해졌다 | 결과를 바꾸는 값과 전파 범위 |
| 예외 시나리오 | 검토한 실패·거절 분기가 기록되었고, 적용되는 결과가 정해졌다 | 이미 기록되었거나 적용 가능한 미정 분기만 묻는다. 빈 결과는 유효할 수 있으며 실패로 단정하지 않는다 |
| 완료 조건 | 정상 시나리오와 적용 가능한 규칙·예외에 관찰 가능한 `AC`가 연결되어 있다 | 기록된 분기 중 AC가 빠졌거나 결과가 미정인 항목 |
| 이벤트 흐름 | `event-storming`의 hotspot이 모두 `해결`이고 정책이 규칙·예외와 모순되지 않는다 | 남은 hotspot |

## 문서 공통 행

| 항목 | `SETTLED`인 경우 | 비어 있을 때 묻는 것 |
|---|---|---|
| 범위·비목표 | 포함은 요청 원문과 확정 항목으로 추적되고, 제외는 요청이 하지 않는 일로 적혔다 | 포함 여부가 갈리는 경계 |
| 우선순위·트레이드오프 | 업무끼리 충돌하는 경우가 없거나 앞서는 쪽이 정해졌다 | 충돌할 때 앞서는 업무 |
| 업무 상태·전이 | 상태를 가진 대상마다 상태와 전이가 정해졌다. 상태가 없으면 `NOT_APPLICABLE` | 빠진 상태·전이 조건 |
| E2E 시나리오 | 핵심 BIZ를 끝까지 따라가는 흐름이 있고 모든 단계가 INV·AC·BIZ에서 나온다 | 시나리오에 필요한데 요구에 없는 동작을 넣을지 |
| 서브도메인·바운디드 컨텍스트 | SD 표가 `confirmed`이고, 분류와 묶음 경계가 각각 사용자 결정으로 추적되며, 모든 BIZ가 `### 1.1` 표의 컨텍스트 하나에 속한다. SD는 앞선 stage에서 사용자가 정했으므로 다시 묻지 않는다. 컨텍스트 소속은 `requirements-fix` 뒤에 `bounded-context`가 정하고 이 행을 확인하므로 `requirements-fix`는 분류하지 않는다 | 표에서 빠진 BIZ |
| 용어 | 문장이 `## 3` 용어 표의 말만 쓰고, 컨텍스트마다 뜻이 다른 말은 컨텍스트별 줄이 있다 | 표에 없는 새 혼용어의 뜻 |
| 서브도메인 간 이벤트 | `## 4` 표의 받는 쪽 반응이 받는 BIZ의 규칙·예외와 맞는다 | 반응이 정해지지 않은 이벤트 |

## 확정 조건

- 모든 행이 `SETTLED` 또는 `NOT_APPLICABLE`이다.
- 사용자 결정으로 쓴 항목은 요청 원문, 채택 후보, `answers.json`, 사용자 수정 지시 중 하나를 출처로 갖는다. 에이전트 제안 항목은 그렇게 표시되어 있고 요청 범위를 넓히지 않는다.
- 중요 정책·성능 목표·보안 기준에 사용한 외부 주장이나 실측은 해당 요구에서 저장된 Claim/Evidence로 추적된다. 선택지별 근거와 적용 조건을 비교했고, 단위·부하나 보호 대상·적용 판본 등 결과를 바꾸는 전제를 확인했다. 확인되지 않은 필수 기준은 확정으로 처리하지 않는다.
- 채택한 `CAND`는 모두 어느 BIZ 항목으로 들어가 있다. 기각·보류·`요청 범위 밖 관찰`은 들어와 있지 않다.
- `INV`와 `EX`마다 이를 확인하는 `AC`가 하나 이상 있다.
- `6.1`의 ACT 연결, 시나리오 클래스, 이유 있는 N/A, 각 SC/INV/EX에서 AC까지의 추적이 닫혔다.
- 서로 모순되는 항목, 단위·정밀도를 사용자가 말하지 않았는데 끼워 넣은 문구가 없다.
