# Review routing

`to-ticket` owns plan authoring and review remediation. After authoring, it returns a provider-neutral `REVIEW_REQUIRED` handoff for a fresh read-only `plan_reviewer`; the caller runs and records the reviewer, then resumes `to-ticket` with the verified result. `to-ticket` revises findings and repeats until the canonical planning review is current and passing. Tracker publication is a separate `tracker-publish` workflow stage.

After canonical plan writing, `to-ticket` returns `REVIEW_REQUIRED` for exactly `plan-review` / `plan_reviewer`. Its caller creates an attempt with `harness-plan-review.mjs begin`, passes the returned `reviewer_input_ref` to a fresh reviewer started with an empty context, and records the attempt with `harness-plan-review.mjs record --attempt <id>`. The subagent hook supplies the verdict, findings and reviewer identity; neither `to-ticket` nor its caller fabricates them. The referenced runner-owned JSON contains the exact admitted file contents and hashes; use it as the complete current snapshot and never discover review inputs by searching `.io` or reading archived restart documents. The reviewer must assess the admitted planning workspace and exact admitted design documents (requirements, tactical design, glossary and map, technology/UI/API/data decisions), index, tickets, and GitHub publication text when configured. It must not require the implementation target to be that workspace or prescribe an implementation target; use the declared return root when no explicit target was requested. The caller resumes `to-ticket` with its verified record. A `revise` verdict causes the same author execution to repair the plans and request a new attempt with a different reviewer. A `pass` verdict completes the stage only after `check --phase planning` confirms the canonical review is current. Before dispatching `tracker-publish`, the orchestrator presents the full reviewed plan set and final publication bodies and obtains the user's own publication reply, which it passes to the runner verbatim.

The reviewer input is the whole snapshot on the first attempt. Re-review uses `review_delta`, prior findings, and directly affected relationships; ambiguous scope requires reading the full affected document. The reviewer returns only its verdict and findings. The runner binds the exact admission file and input hashes to the attempt; `record` compares that admission with the active ledger and evaluates the current workspace snapshot, recording stale results as stale.

Record actual author execution IDs and reviewer IDs, keep `fork_turns: none`, and never treat a user answer as a review pass. After three substantive attempts without a pass, ask the user to resolve the concrete scope or decision. The completion runner and publisher stage both verify the latest review against current files; tracker changes happen only in the publisher stage after the precheck passes.

**Provider-neutral reviewer handoff.** Codex and Claude Code use the same caller handoff because the stage subagent cannot start the native reviewer in either provider. After canonical plans and index are written and `check --phase planning` has no preparation errors, return `action_required/REVIEW_REQUIRED` with exactly `skill: plan-review` and `agent_profile: plan_reviewer`. The caller runs `harness-plan-review.mjs begin`, starts a fresh reviewer with the returned `reviewer_input_ref`, runs `record --attempt <id>`, then passes the recorded result back to `to-ticket` with `--feedback`. The plan-review execution contract validates reviewer identity and admission; the stage must not write verdicts or identity itself. Reject a handoff naming another skill/profile or lacking the reviewed attempt. A `revise` response returns to this stage to address findings and start a new attempt; `pass` completes only after `check --phase planning` confirms the canonical snapshot is current.
